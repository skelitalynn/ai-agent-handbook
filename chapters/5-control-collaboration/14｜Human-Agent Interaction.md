# Human-Agent Interaction

> 本文讨论人怎样向 Agent 提供意图、观察执行、授权副作用、纠正路径并在失败时接管。它建立在第 13 章的持久 Workflow 之上：Human-in-the-loop 不是聊天界面中的一个确认框，而是一组与 Run State、风险策略和责任边界绑定的控制机制。

## 面试速记

### 背诵提纲

**1. 定义**

Human-Agent Interaction 是人在 Agent 生命周期中表达目标、补充信息、监督进度、授权行动、纠正结果和承担业务决策的交互闭环；有效控制要求人拥有足够信息、权限、时间和可执行的替代选项。

**2. 完整链路**

用户目标 → 澄清或 Elicitation → 计划与风险预览 → 自动执行或审批 → 语义进度与中间产物 → 纠正、取消或恢复 → 结果确认与审计。

**3. 补充信息**

- **Clarification**：当缺失的是用户意图、偏好或业务取舍时，Agent 应提出最小必要问题，而不是自行假设。
- **Elicitation**：系统或协议通过客户端请求结构化补充信息，并保留接受、拒绝和取消等不同结果。

**4. Human-in-the-loop 与审批**

HITL 应放在高不确定性、高影响、不可逆或越权风险的决策点；Approval 必须绑定具体 Action、参数、范围、期限、审批人和策略版本，而不是笼统批准整个 Agent。

**5. 生命周期控制**

Interrupt 表示运行时因外部输入而中断，Pause 保存可恢复状态，Resume 从同一 Run 继续，Cancel 请求停止后续工作；取消不能自动撤销已经提交或正在执行的副作用。

**6. 进度与产物**

Streaming 只是一种增量传输机制，真正的进度应展示阶段、已完成动作、当前等待、失败和可检查 Artifact；不应把 Token 流或隐藏 Chain-of-Thought 冒充业务进度。

**7. 纠正与重新规划**

用户纠正应写入结构化状态并使依赖旧输入的计划、审批和中间结果失效；已经发生的外部效果需要补偿或追加更正，不能仅修改聊天历史。

**8. 失败与不确定性呈现**

系统应区分拒绝、权限阻止、信息不足、暂时故障、永久失败和结果未知，明确说明已完成与未完成部分、证据、可恢复动作和人工接管入口。

**9. 自动化与责任**

自动化程度应由风险、可逆性、可观察性和用户预授权共同决定；模型提出行动，Runtime 执行策略，外部系统校验权限，组织定义责任，用户审批不能替代这些控制。

### 高频对比

| 交互 | 要解决的问题 | 用户返回的内容 | 不应混淆为 |
| --- | --- | --- | --- |
| 澄清 | 目标、偏好或边界不明确 | 自然语言选择或补充说明 | 对副作用的授权 |
| Elicitation | 运行时缺少结构化输入或外部流程 | 符合 Schema 的数据，或接受/拒绝/取消状态 | Agent 自由追问的统称 |
| Approval | 一项明确行动是否允许执行 | 对具体 Action Snapshot 的决定 | 对未来任意行动的永久授权 |

### 高频问题

#### 问题1：为什么让用户审批每一次工具调用反而不安全？

频繁、低价值且难以理解的确认会造成 Approval Fatigue，用户可能机械点击。应按风险分级，把低风险动作自动化，把相关动作聚合为边界清楚的计划，并在范围、参数或风险发生实质变化时重新审批。

#### 问题2：一项操作已经获批，Resume 时为什么还要重新校验？

审批等待期间参数、权限、资源状态和策略版本都可能变化。Runtime 应核对审批绑定的 Action Digest、有效期和前置条件，避免把旧批准用于新意图或遭遇 Time-of-check to time-of-use 问题。

#### 问题3：用户点击 Cancel 后，为什么工具仍可能产生结果？

取消通常是协作式请求，已经发出的网络调用或外部事务可能无法被瞬间终止，完成结果还可能晚到。系统必须继续记录晚到结果，并对已发生效果执行补偿或提示人工处理。

#### 问题4：怎样展示 Agent 进度而不暴露隐藏 Chain-of-Thought？

展示可观察事实，例如当前阶段、工具开始与结束、证据来源、结构化短依据、中间 Artifact 和阻塞原因。内部推理文本既不稳定也可能含敏感信息，不能作为进度或审计依据。

#### 问题5：怎样评测 Human-in-the-loop 设计是否有效？

同时测量漏拦截高风险动作、无必要打断、审批理解正确率、纠正成功率、取消响应、人工处理时延和任务结果。只统计“有多少审批被点击通过”无法证明用户拥有有效控制。

## 有效的人类控制不是在循环里随便插入一个人

Agent 与普通聊天机器人的差异在于它会改变外部世界。只要系统能够发邮件、修改文件、提交订单或调用企业服务，交互设计就不再只是“答案好不好看”，而是要回答：Agent 是否理解了目标，人能否看到它正在做什么，哪些动作必须由谁批准，发生偏差时是否来得及纠正，以及失败后责任落在哪里。

Human-in-the-loop（人在回路中，HITL）常被简化成“工具调用前弹窗”。这只覆盖了一类控制点。完整闭环至少包含五个阶段：意图建立、执行前授权、执行中可见性、执行后纠正和异常接管。某些任务应在计划阶段由人决定方向，某些只需在不可逆提交前审批，某些则需要领域专家审查最终结果。

```text
表达目标
   ↓
是否缺少意图或必要数据？ ──是──→ 澄清 / Elicitation
   │ 否                                  │
   ↓                                     └──拒绝或取消→ 替代路径 / 停止
生成受约束计划
   ↓
按风险决定：自动执行 / 计划级审批 / 单动作审批 / 禁止
   ↓
语义进度 + 中间 Artifact
   ↓
完成 / 用户纠正 / 取消 / 失败接管
```

“让人参与”不自动带来安全。人如果看不到真实参数、无法理解影响、没有拒绝选项，或者在副作用已经发生后才收到通知，就不具有有效控制。反过来，让人逐条确认几十个无关紧要的读取操作，也会消耗注意力并降低真正高风险提示的辨识度。

## 澄清、Elicitation 和 Approval 的问题不同

Agent 应先判断缺失信息能否从环境中可靠取得。事实性信息可以通过受信工具查询，例如订单当前状态；偏好、意图和价值判断通常只有用户能决定，例如“优先退款还是换货”。后一类信息若不澄清，模型只能把猜测伪装成决定。

好的澄清问题满足三个条件。第一，只问会改变计划或结果的最小信息；第二，说明为什么需要，而不是把内部术语抛给用户；第三，提供少量真实可选项，同时允许用户补充自己的答案。已知默认值可以展示但不能冒充用户选择，高影响场景中的沉默也不能当作同意。

Elicitation 是更具体的运行时或协议机制。在当前稳定的 Model Context Protocol（MCP）规范中，Server 可以经 Client 请求额外信息。Form Mode 用 Schema 收集结构化、非敏感数据；URL Mode 可以把需要认证或敏感输入的流程交给安全的外部页面。响应区分 `accept`、`decline` 和 `cancel`：Decline 表示用户明确拒绝，Cancel 表示关闭或暂未作出决定，服务端可以选择不同后续行为。

普通聊天中的追问不自动成为 MCP Elicitation。无论采用哪种实现，都应显示请求来自哪个组件、需要哪些字段以及用途；结构化响应需要在 Client 和 Server 两侧验证。密码、API Key 等敏感信息不应通过普通表单 Elicitation 收集，更不能进入模型上下文或 Trace。

Approval 则发生在行动已经足够明确之后。用户不是在补充“做什么”，而是在决定“是否允许执行这个具体动作”。如果一个所谓审批页还隐藏着目标资源、收件人、金额或不可逆后果，用户实际无法授权它。

## 风险策略决定控制点，模型不能给自己定级

风险不是工具名的固定标签，而是动作、参数、作用域、主体、环境和可恢复性的组合。同一个 `send_email`，保存草稿和向全公司发送通知的风险不同；同一个读取工具，访问公开网页和读取工资数据库也不同。模型可以描述意图，但 Runtime 应依据组织策略、工具元数据和当前身份计算风险。

下面是一种工程起点，不是跨业务通用标准：

| 风险特征 | 常见控制方式 | 例子 |
| --- | --- | --- |
| 只读、低敏感、可审计 | 预授权后自动执行 | 查询公开文档 |
| 可逆、影响范围有限 | 自动执行并提供 Undo，或计划级批准 | 创建草稿、修改临时文件 |
| 外部可见、财务、权限或隐私影响 | 绑定参数的单动作审批 | 发信、付款、授予访问权 |
| 不可逆且影响面大 | 双人复核、延迟提交或人工执行 | 批量删除、生产数据迁移 |
| 明确违反政策 | 直接阻止，不提供“继续批准” | 导出无权访问的敏感数据 |

审批请求至少需要绑定：Run 和 Tool Call ID、动作与参数快照、目标资源、风险与可逆性、预计影响、策略版本、审批范围、有效期和审批人身份。可以对这个 Snapshot 计算 Digest；Resume 前再次计算，如果收件人、金额、文件路径或 Plan Revision 已改变，旧批准立即失效。

```text
模型提出 Action
   ↓
Runtime 按当前身份和参数分类风险
   ├── 自动允许 → 执行
   ├── 禁止     → 阻止并记录策略原因
   └── 需审批   → 保存 Action Snapshot + Digest + Expiry
                         ↓
                     用户决定
                         ↓
              Resume 前重算 Digest 并检查权限
```

“Always allow” 只能是一项有边界的策略，例如同一 Run 内对某个只读工具和特定资源范围有效。它不应把一次低风险查询的同意扩张为对该工具未来所有参数的永久授权。审批人身份也必须由认证和授权系统确认，不能相信模型或表单里的一句“我是管理员”。

## Interrupt、Pause、Resume 与 Cancel 是不同状态

Interrupt 是触发控制流交还的事件，例如需要审批、缺少输入或策略命中；Pause 是持久化后的等待状态；Resume 使用同一 Run 身份和已保存决定继续；Cancel 是停止后续工作的请求。UI 可以把这些动作放在相邻位置，但 Runtime 不能把它们压成一个布尔值。

跨进程、跨会话恢复要求把 Run State 保存到数据库、队列或工作流引擎，而不是只留在浏览器或 Python 内存。状态通常包含未决 Tool Call、已给出的决定、Token/成本使用、计划版本、Trace 关联信息和必要业务上下文。OpenAI Agents SDK 的 HITL 流程也是先把中断结果转换为可序列化的 `RunState`，记录批准或拒绝，再用原始顶层 Agent 恢复同一 Run。

序列化状态本身可能含用户上下文、工具参数、Trace 元数据或会话设置，应按持久敏感数据处理：最小化、加密、隔离租户、控制保留期和访问审计。长时间等待还会跨越 Agent、Prompt、工具和 SDK 发布，因此需要保存版本标记，并把旧状态路由到兼容代码。

Cancel 不等于原子回滚。Runtime 应先记录取消意图，不再派发新动作，再向正在运行的 Activity 传播取消。已经发送的请求可能忽略取消或在信号到达前成功，晚到结果仍要进入 Trace。第 13 章的补偿和对账机制负责处理已经发生的副作用；前端不能在用户点击取消后立刻显示“所有操作均已撤销”，除非系统已经验证这一事实。

## Streaming 传输事件，进度必须表达业务事实

Token Streaming 可以改善首字延迟，但 Token 数量与任务完成度没有稳定关系。Agent 可能输出大量解释却没有执行任何工具，也可能沉默很久完成关键查询。可靠进度应来自 Workflow 和 Activity 的语义事件，而不是根据生成文本猜测百分比。

对用户有用的进度通常包括：

- 当前阶段和已完成阶段，例如“已检索 4/6 个数据源”；
- 正在执行的外部动作及其安全摘要，而非完整敏感参数；
- 当前等待的是工具、限流、人工审批还是用户输入；
- 已产生的中间 Artifact、版本和可检查链接；
- 失败、重试、降级和取消是否已经生效；
- 仅在工作量可估算时展示百分比，否则用阶段和完成项表达。

流结束也未必等于 Run 已成功。某些 SDK 会在最后一个可见 Token 后继续持久化会话、处理审批状态或压缩历史；需要读取显式完成状态。暂停等待审批时，流可以正常结束，但 Run 仍处于 `WAITING_APPROVAL`，后续 Resume 是同一个任务，不是新用户轮次。

中间 Artifact 比“正在思考”更有验证价值。搜索 Agent 可以展示来源清单，Coding Agent 可以展示 Diff 和测试结果，报告 Agent 可以展示带版本的提纲。Artifact 必须标明 Draft/Final、生成时间、证据和是否已验证；否则用户可能把过期草稿当成最终结果。

系统可以展示简短的 Observable Basis，例如“订单金额超过策略阈值，需要财务审批”，但不应请求、保存或公开隐藏 Chain-of-Thought。后者既不是稳定接口，也可能泄露敏感上下文；权限规则、工具参数、环境结果和状态转移才是可审计证据。

## 纠正必须改变状态和依赖，而不只是追加一句话

用户在执行中说“不是这个客户”“不要发邮件，先保存草稿”，代表前提或目标发生变化。只把这句话追加到聊天历史，同时保留旧 Plan、旧审批和已缓存 Tool Call，会让 Agent 在两个互相冲突的世界模型中继续运行。

纠正应记录目标对象、修改内容、操作者和 Plan Revision，并计算影响范围：

```text
纠正 Action A 的输入
   ↓
使 A 的旧审批和缓存失效
   ↓
沿依赖图标记 B、C 的结果为 Stale
   ↓
重新规划或重新执行受影响子图
   ↓
保留未受影响结果和完整审计记录
```

如果受影响动作尚未执行，可以取消并替换；如果只是可编辑草稿，可以生成新版本；如果外部邮件已经发送，则不能把记录标记为“未发生”，只能发送更正、撤回（若系统支持）或提示人工处理。用户纠正是业务输入，不是万能回滚命令。

反馈也要区分用途。对当前 Run 的“改成更正式的语气”应立即修改 Artifact；对未来偏好的“以后都先给我预览”可以在用户同意后写入 Memory；用于产品改进的评分进入 Eval 数据。一个没有原因和上下文的点赞/点踩，通常不足以自动改变权限策略或长期偏好。

## 拒绝、失败和不确定性需要可行动的表达

Agent 最危险的失败之一是界面显示得像成功。结果页应把状态分开：

- **Refused**：模型或产品政策拒绝执行，说明允许范围内的替代方案。
- **Blocked**：权限或 Runtime Policy 阻止动作，给出所需角色或安全路径。
- **Needs input**：缺少只有用户能决定的信息，提出具体问题。
- **Failed**：已知没有完成，保留错误分类、已完成步骤和重试入口。
- **Unknown**：超时或断线后无法判断外部副作用是否发生，应先对账而非盲目重试。
- **Partially completed**：明确列出成功、失败、仍在运行和需要补偿的部分。

不确定性应针对决策表达，而不是机械附加“我可能会错”。系统需要说明不确定来自哪里、会影响哪项行动、可以用什么证据降低，以及在当前风险下为何选择继续、降级或询问。高影响结论最好显示来源和更新时间；模型自报的置信分数未经校准时不能直接当成概率。

失败信息既要对用户可理解，也要保留工程诊断键。用户看到“付款结果未知，正在核对，请勿重复提交”；运维人员可以通过 `run_id`、`tool_call_id` 和 Trace 找到具体 Timeout、Attempt 和外部请求标识。直接展示堆栈或第三方原始错误既泄露信息，也未必能帮助用户行动。

## 自动化程度由风险和可恢复性共同决定

自动化不是从“手工”到“全自动”的单一开关。同一 Agent 可以自动读取公开信息、在计划级别请求确认、对付款逐笔审批，并完全禁止修改权限。决定控制强度时至少考虑影响大小、发生概率、可逆性、检测速度、证据质量和用户是否预先授权。

Approval Fatigue 的根因不是弹窗数量本身，而是每次打断都要求用户花注意力，却没有提供新的、可判断的信息。降低疲劳可以采用：

- 对低风险、重复且边界稳定的动作使用预授权；
- 在执行前让用户审核结构化 Plan，而不是逐条确认相同策略内的步骤；
- 把同一目标和作用域内的动作成组展示，但保留高风险单项；
- 明确与上次相比变化了什么，只对范围扩大或参数变化重新审批；
- 让 Decline 和 Cancel 一样容易，避免默认勾选和诱导性文案；
- 记录用户是否理解动作后果，而不是用高通过率证明设计优秀。

计划级批准不能变成空白支票。Plan 应包含允许的工具、资源范围、最大成本、外部接收者和失效条件；模型新增子任务、扩大数据范围或遇到更高风险动作时，必须回到审批点。

## 责任边界需要组织制度和技术证据共同支撑

NIST AI RMF 强调，应明确区分使用、监督和管理 AI 系统的人类角色。工程上可以把责任拆开：产品与业务负责人定义可接受风险和禁止行为，安全团队定义身份和权限策略，Agent 提出结构化行动，Orchestrator 强制状态与预算，Tool Adapter 校验参数，外部系统执行最终授权，用户提供意图和需要其判断的决定，运维人员处理事故与人工修复。

模型不能因为“用户好像想要”就获得权限；Runtime 不能因为弹过审批框就把责任全部转给用户；用户批准也不能证明模型给出的事实正确。组织仍需保证提示信息真实、控制有效、审批人有能力和权限，并为不可逆结果准备申诉、补偿和审计路径。

评测 Human-Agent Interaction 要同时覆盖安全性和可用性。除了端到端任务成功率，还应统计高风险漏拦截率、低风险误打断率、审批决定时间、审批后参数变更拦截率、Cancel 到停止派发的时间、晚到副作用数量、纠正后 Stale 结果复用率、人工接管率和用户放弃率。还应通过情景测试检查用户是否能准确复述即将批准的动作，而不只测试按钮能否点击。

## 最小实现把有效控制转成可测试不变量

本章示例 [`interaction_controller.py`](../../examples/14-human-agent-interaction/interaction_controller.py) 使用 Python 标准库实现一个可序列化的交互控制面。Tool Risk 来自 Runtime Policy，而不是模型字段；低风险动作自动授权，高风险动作生成绑定 Digest 和 Expiry 的请求，禁止动作没有可供用户绕过的审批入口。

执行前会根据当前参数重新计算 Action Digest：

```python
if current_digest != action.digest:
    action.status = ActionStatus.INVALIDATED
    raise InvalidState("action arguments changed after authorization")
```

示例还保留 `accept`、`decline`、`cancel` 三种输入结果，支持 JSON Round-trip 后恢复审批状态，并让纠正沿依赖图使后续 Action 失效。已完成的外部副作用不能靠 Correction 改写，必须先进入 Compensation 流程；Cancel 后仍允许记录在途 Action 的晚到结果。

15 项测试验证自动授权、风险审批、禁止策略、审批人权限、参数绑定、过期、三态决定、结构化输入、跨进程序列化、依赖失效、取消、晚到结果和公开进度不泄露工具参数。示例没有实现真实身份系统、加密存储、分布式 Workflow 或 UI，无意替代生产权限与审批服务。
