# Retrieval、RAG 与 Agentic Search

> 本文建立外部知识进入 Agent 上下文的完整链路：从数据摄取、切分、权限与索引生命周期，到稀疏/稠密检索、融合、重排、证据生成和迭代搜索。它以第 08、09 章的评测与追踪为反馈机制，并为第 11 章区分知识检索与长期 Memory。

## 面试速记

### 背诵提纲

**1. 三个概念**

Retrieval 从授权候选集中选择相关证据；RAG 把检索结果加入模型输入后生成答案；Agentic Search 允许 Agent 根据中间结果继续改写或拆分查询，并在满足终止条件时停止。

**2. 完整链路**

```text
数据源 → 解析与规范化 → 权限元数据 → 切分 → 稀疏/稠密索引
查询 → 权限与属性过滤 → 召回 → 融合/重排 → 证据上下文
     → 生成与引用 → Retrieval、Answer、Security Evals
```

**3. 数据摄取**

每个 Chunk 都应保留稳定文档 ID、版本、来源、权限和定位信息；索引是源数据的派生视图，更新要避免新旧版本混杂，删除要传播到所有索引和缓存。

**4. 切分**

Chunk 太小会丢失语境，太大会降低检索粒度并占用更多上下文；应按文档结构、查询类型和模型窗口评测，可使用重叠、标题上下文或父子检索补足边界信息。

**5. 召回与排序**

稀疏检索擅长精确词项和标识符，稠密检索擅长语义相近但词面不同的表达；混合检索先分别召回再融合，重排器用更高成本对较小候选集重新判断相关性。

**6. 权限边界**

Tenant、ACL 和属性过滤必须在候选进入检索评分前生效；先全库 Top-k 再删除越权结果既有泄露风险，也会让合法结果被越权候选挤出。

**7. RAG 的正确性边界**

RAG 能引入可更新、可追溯的外部证据，但“检索到相关文档”“模型依据证据回答”“引用真正支持结论”是三个独立条件，必须分别评测。

**8. Agentic Search**

Agentic Search 适合查询需要拆解、证据不足时需要追问或多源交叉验证的任务；必须限制最大步数、时间、成本、重复查询和可访问数据源，固定路径问题优先使用普通 RAG。

**9. 评测与诊断**

检索层评测 Recall@k、MRR 或 nDCG，生成层评测正确性、忠实性和引用质量，系统层评测权限、时效、延迟和成本；完整 Trace 用于定位失败发生在哪一层。

### 高频对比

| 方案 | 主要信号 | 擅长场景 | 主要局限 |
| --- | --- | --- | --- |
| 稀疏检索 | 词项频率与倒排索引 | 错误码、产品编号、人名和原词匹配 | 对同义改写和语义表达较弱 |
| 稠密检索 | Embedding 向量相似度 | 词面不同但含义接近的查询 | 可能漏掉精确标识符，依赖模型与语料分布 |
| 混合检索 | 两类结果的名次或校准分数 | 同时包含自然语言和精确词项的业务查询 | 链路更复杂，需要评测融合和重排参数 |

### 高频问题

#### 问题1：为什么只使用向量检索可能找不到错误码或订单号？

Embedding 优化的是语义表示，不保证任意稀有字符串的精确可分性；切分、分词和近似检索还可能进一步损失信号。错误码、ID 和专有名词通常应保留稀疏或字段级精确检索，并与稠密结果融合。

#### 问题2：为什么不能先从全库取 Top-k，再过滤用户无权访问的结果？

越权候选已经参与评分，可能通过分数、摘要、缓存或 Trace 泄露信息；过滤后还可能不足 k 条，因为合法候选早已被挤出。应先建立授权候选集，再在相同边界内完成所有召回和排序。

#### 问题3：答案附带引用，为什么仍然可能不可信？

引用可能只与主题相关，却不蕴含具体结论；模型也可能混合自身参数知识、误读版本或把多段证据错误拼接。需要分别检查引用是否存在、是否指向正确片段，以及片段是否真正支持对应断言。

#### 问题4：为什么增大 Top-k 不一定提高 RAG 质量？

更大的候选集可能提高召回，却会带来无关或冲突证据、挤占上下文并增加延迟。应先看 Recall@k 曲线，再通过过滤、融合、重排和证据压缩决定送入模型的规模。

#### 问题5：什么时候值得把固定 RAG 升级为 Agentic Search？

当单次查询难以表达信息需求，任务需要分解、跨来源验证或根据首轮证据继续追查时才值得引入循环。若查询模式稳定、数据源单一且延迟可预测更重要，固定检索流水线更容易评测和维护。

## 外部知识不是把更多文本塞进 Prompt

模型参数保存的是训练后形成的统计表示，不是可按主键更新、删除和审计的数据库。Context Window 虽能临时承载外部文本，却不会替系统决定应该读取哪一版文档、用户是否有权读取，以及哪些片段真正支持答案。因此，在模型调用之前需要一条独立的数据与检索链路。

Retrieval（检索）只负责从候选集合中选择证据。RAG（Retrieval-Augmented Generation，检索增强生成）在检索之后增加证据组织与生成。Agentic Search 是一种工程上的循环控制方式：Agent 可以观察上一轮结果，决定下一条查询、其他数据源或停止。三者位于同一知识链路的不同位置，而不是同义词。

```text
                         ┌──────────── 离线或异步数据面 ────────────┐
源系统 ─→ 解析 ─→ 规范化 ─→ Chunk + 元数据 + ACL ─→ 索引 ─→ 版本发布
                         └──────────────────────────────────────────┘
                                             │
                                             ▼
                         ┌──────────── 在线查询面 ──────────────────┐
用户 ─→ 身份与查询 ─→ 授权候选集 ─→ 召回 ─→ 融合/重排 ─→ 证据包
                                                         │
                                  ┌──────────────────────┴─────────┐
                                  ▼                                ▼
                            固定 RAG 生成                  Agent 决定继续搜索
                         └──────────────────────────────────────────┘
```

图中最重要的分界是：索引不是事实源，授权也不是排序后的清理步骤。源系统负责文档事实和访问策略，索引只是为了查询而建立的派生视图；在线查询必须携带已验证身份，在授权范围内完成检索。

## 数据摄取决定了系统能够检索什么

摄取（ingestion）把源数据转换为可检索对象。网页、PDF、工单和数据库记录首先需要解析并规范化；页眉、导航、重复模板和乱码若没有清理，会成为高频噪声。表格、代码块、标题层级和页码却可能是回答问题必需的结构，不能在“纯文本化”时全部丢掉。

一个可维护的文档对象至少需要稳定的 `document_id`、来源定位、版本或更新时间、Tenant、访问控制信息和业务元数据。切分后的每个 Chunk 还需要保存父文档 ID、片段序号以及可返回原文的位置。只有这样，系统才能把召回结果追溯到事实源、生成稳定引用，并在文档变化时找到所有派生数据。

### 切分是在检索粒度与语境之间取舍

检索一般不会把整本手册作为一个候选，因为大对象的向量会混合多个主题，词项统计也难以定位具体答案。把文档切成 Chunk 可以提高定位精度，但切分边界会制造新的信息损失：代词可能离开其指代对象，标题与正文分离，表头只出现在上一段，结论和限制条件落入不同 Chunk。

常见策略不是互斥选项：

- 结构切分优先利用章节、段落、列表、表格和代码块边界；固定 Token 窗口可作为超长结构的第二层限制。
- 重叠窗口让边界附近的信息同时出现在相邻 Chunk，但会增加索引体积并制造近重复候选。
- 上下文化 Chunk 在索引文本中补入标题、父章节或简短文档背景，而返回引用时仍指向原始片段。
- 父子检索用小 Chunk 召回，再向模型提供较大的父级上下文，分离“如何找到”和“读多少”。

不存在通用最佳 Chunk 大小。FAQ、API Reference、法律条款和长篇叙事的结构不同；目标查询是定位错误码还是概括整章，也会改变最佳粒度。选择必须通过真实查询集验证 Recall、上下文噪声、延迟和生成质量，而不能只沿用向量数据库默认值。

### 更新和删除必须覆盖整个派生链

文档更新不能简单追加新 Chunk，否则查询可能同时召回互相冲突的新旧版本。稳妥做法是先用新版本构建完整派生对象，通过版本检查后原子切换可见索引或索引别名，再异步回收旧版本。并发摄取需要拒绝陈旧事件；同一版本出现不同内容则应视为冲突，而不是静默覆盖。

删除也不只是移除一条向量。它至少要传播到稀疏索引、向量索引、重排缓存、Retrieval Cache 和引用服务。异步系统可先写入 Tombstone（删除标记），使查询立即排除对象，再完成物理清理。若访问权限发生变化，也应按安全更新处理：旧 ACL 不能继续留在缓存或某一类索引中。

```text
源事件：document_id=D，version=7
        ↓
校验版本与访问策略
        ├── 小于当前版本 → 拒绝陈旧事件
        ├── 同版本不同内容 → 报告冲突
        └── 新版本
              ↓
          完整构建新 Chunk 与索引项
              ↓
          原子切换 version=7 为可见版本
              ↓
          清理旧索引项与缓存
```

## 查询链路先建立候选边界，再计算相关性

在线请求至少包含查询文本、已验证的主体身份、Tenant 和允许参与过滤的业务属性。系统先把这些信息转换为数据库或搜索引擎能够强制执行的过滤条件，再在过滤后的集合中执行稀疏和稠密召回。把 ACL 只写进 Prompt 没有约束力，因为模型看见文档时泄露已经发生。

权限预过滤还有一个容易忽略的质量原因。假设全库 Top-10 中有八条属于其他用户，事后删除只剩两条；本来排在全库第 11～18 位的合法文档不会自动补进来。正确做法是在授权集合内重新定义排名问题。

### 稀疏检索保留词项证据

倒排索引从词项映射到包含它的文档。BM25 是常用稀疏排序函数，它提高查询词在当前文档中出现的得分，同时对高频词和超长文档进行校正。其一种常见形式为：

```text
BM25(q, d) = Σ IDF(t) · tf(t,d) · (k1 + 1)
                 ───────────────────────────────
                 tf(t,d) + k1 · (1 - b + b·|d|/avgdl)
```

这里的具体参数不是重点。关键是分数来自可观察的词项匹配，所以它擅长错误码、函数名、产品编号和专有名词。中文等没有天然空格边界的语言需要合适的分词、字符级索引或专用分析器；正文示例里的正则 Tokenizer 只是算法演示。

### 稠密检索把查询和 Chunk 映射到同一向量空间

稠密检索使用 Embedding 模型分别编码查询和 Chunk，并按点积或余弦相似度选择相近向量。双编码器允许文档向量预先计算，查询时只编码一次查询；大规模系统通常使用 Approximate Nearest Neighbor（近似最近邻）索引，以少量召回损失换取速度与内存效率。

语义相似不等于答案蕴含。一个讨论“退款”的 Chunk 可能和“取消订单后多久到账”很接近，却没有说明时间；Embedding 模型还会随语言、领域和版本改变排序。因此，稠密召回要通过业务数据评测，不能把相似度阈值当作事实正确性阈值。

### 混合检索与重排解决不同阶段的问题

混合检索分别运行稀疏和稠密召回，再合并结果。两类原始分数通常不在同一尺度上，直接相加会让某一检索器因分数分布占优。Reciprocal Rank Fusion（倒数排名融合，RRF）使用名次计算贡献：

```text
RRF(d) = Σ 1 / (c + rank_i(d))
```

它避免直接比较不同分数，但融合常数、各路候选数和权重仍需评测。另一种做法是先校准分数，再做加权融合。

重排（reranking）位于召回之后。它让更昂贵的模型同时观察 Query 与候选 Chunk，判断二者的细粒度关系，再从几十或几百个候选中选择较少证据。重排不能找回召回阶段完全漏掉的文档；候选集过大又会增加延迟和成本。因此，应先优化 Recall，再决定是否用重排改善前几名精度。

```text
授权候选集
   ├── 稀疏召回 ─→ Top-N ─┐
   └── 稠密召回 ─→ Top-N ─┤
                           ↓
                       去重与融合
                           ↓
                    可选的高成本重排
                           ↓
                   Top-K 证据及来源定位
```

## RAG 需要把证据契约延伸到生成结果

RAG 的“Augmented”不是简单字符串拼接。证据构建器需要在 Context Window 和预算内决定保留哪些 Chunk、如何去重、是否展开父文档、怎样呈现版本冲突，以及如何让引用 ID 与文本保持相邻。模型还应得到明确契约：外部材料是待分析的数据，不是高优先级指令；证据不足或冲突时应报告不确定性，而不是补写看似合理的事实。

```text
Query + Identity
      ↓
授权检索与重排
      ↓
Evidence Pack：chunk_id、来源、版本、正文
      ↓
模型按证据生成断言并返回引用 ID
      ↓
运行时验证引用存在且调用者仍有权限
      ↓
返回答案、引用和必要的不确定性说明
```

这个过程包含至少三种不同正确性：

1. 检索相关性：支持答案的证据是否进入候选和最终上下文。
2. 生成忠实性：模型的具体断言是否能够从所给证据推出。
3. 引用正确性：引用是否指向支持相邻断言的正确版本与位置。

因此，“有引用”只是输出结构，不是正确性证明。运行时可以验证引用 ID 存在、属于本次授权结果且版本仍有效；语义上是否支持断言，还需要规则、模型评分或人工标注的 Eval。若资料之间冲突，系统应保留来源与时间信息，让生成策略显式选择最新权威版本或向用户说明冲突。

## Agentic Search 把检索升级为受控决策循环

固定 RAG 为每个请求执行预先定义的一次查询、召回和生成。它的优势是延迟、成本和失败面容易预测。复杂研究任务却可能在第一轮后才暴露真正的信息缺口，例如需要先确定产品版本，再查该版本的错误码，最后到变更日志核对修复状态。

Agentic Search 让模型或规划器根据当前证据选择下一步。常见动作包括拆分问题、生成同义查询、选择结构化数据库或网页搜索、打开高价值来源、追踪引用，以及在证据冲突时寻找第二来源。这里的 Agentic 不意味着无限自主；外层运行时仍负责权限、工具 Allowlist、预算、去重和终止。

```text
初始问题
   ↓
规划查询与数据源
   ↓
执行授权检索并记录 Trace
   ↓
证据是否足够且一致？
   ├── 是 → 组织证据并生成答案
   └── 否
         ↓
      是否超过步数、时间、成本或重复查询限制？
         ├── 是 → 返回已有证据与未解决问题
         └── 否 → 改写/拆分查询，再次检索
```

“证据足够”不能只依赖模型一句自我判断。系统可以同时要求关键子问题都有来源、目标字段非空、相互冲突已解决或显式标注，并设置最大步数、墙钟时间、Token/搜索成本和来源访问上限。连续生成等价查询、只在同一结果页循环或多轮没有新增高质量证据时，也应提前停止。

引入循环会扩大非确定性和攻击面。外部页面可能包含 Prompt Injection；搜索工具可能跨越不同权限域；同一事实在多轮中可能被重复计费和塞入上下文。因此，只有离线 Eval 证明固定检索无法满足任务，而多步策略带来的质量收益超过延迟、成本和安全代价时，才应升级为 Agentic Search。

## 评测必须拆开检索、生成和系统边界

只看最终答案会掩盖两类相反问题：检索器可能没有找到证据，但模型依靠参数知识碰巧答对；检索器也可能找到正确证据，却被 Context 构建器截断或被模型忽略。评测集应同时保存查询、授权身份、期望相关文档或 Chunk、可接受答案、不可回答条件和数据版本。

检索层常见指标包括：

- Recall@k：至少一个或全部相关证据是否出现在前 k 个结果，适合判断召回是否漏证据。
- MRR：第一个相关结果排名的倒数，强调尽早出现首个答案证据。
- nDCG：在存在多级相关性时同时考虑相关程度和排名位置。

这些指标的前提是相关性标注可信。单个公开 Benchmark 不能代表企业语料中的缩写、权限、时间性和长尾查询；BEIR 的异构结果也说明检索方法会随数据集明显变化。业务评测至少应覆盖自然语言改写、精确 ID、跨语言查询、无答案、冲突版本、权限隔离和删除后不可检索。

生成层再评估 Answer Correctness、Faithfulness（对证据的忠实性）、引用覆盖与引用蕴含。系统层记录 P50/P95 延迟、索引新鲜度、每次查询候选数、重排和模型成本，并执行越权 Canary 测试。Agentic Search 还要评估步数分布、重复查询率、停止原因、来源多样性以及每增加一步带来的边际质量。

第 09 章的 Trace 应为每次召回、过滤、融合、重排和模型调用创建可关联 Span，但不能默认记录未经脱敏的完整文档。诊断时沿以下路径缩小问题：

```text
答案错误
   ↓
期望证据在索引中吗？ ── 否 → 摄取、解析、版本或删除问题
   ↓ 是
授权候选集中存在吗？ ── 否 → 身份、ACL 或属性过滤问题
   ↓ 是
进入召回 Top-N 吗？ ── 否 → Query、分词、Embedding 或 ANN 问题
   ↓ 是
融合/重排后保留吗？ ── 否 → 排序与阈值问题
   ↓ 是
进入最终 Context 吗？ ── 否 → 去重、预算或证据构建问题
   ↓ 是
模型按证据回答吗？ ── 否 → Prompt、模型或输出验证问题
```

## 最小实现验证关键不变量

本章示例 [`hybrid_retriever.py`](../../examples/10-retrieval-rag-agentic-search/hybrid_retriever.py) 使用 Python 标准库实现滑窗切分、BM25、向量余弦相似度、RRF、版本化替换、删除和 Agentic Search 外层循环。生产系统应换成真实分词器、Embedding 服务和持久化索引，但关键顺序不应改变：

```python
candidates = [
    chunk
    for chunk in self._chunks.values()
    if chunk.tenant_id == tenant_id
    and principal in chunk.allowed_principals
]

lexical_scores = self._bm25(query_tokens, candidates)
dense_scores = {
    chunk.chunk_id: cosine(query_embedding, chunk.embedding)
    for chunk in candidates
}
```

这里先形成授权候选集，再把同一集合交给两类评分器。测试还验证了精确标识符由词项检索找回、同义表达由注入的概念向量找回、新版本替换旧 Chunk、陈旧删除被拒绝，以及重复查询和最大步数可以终止搜索循环。测试用概念向量只是可控 Test Double，不代表真实 Embedding 模型能力。

以 2026-07-22 的 OpenAI 官方文档为例，Vector Store 可托管文件切分、Embedding 和索引，并支持属性过滤、排序选项、分数阈值与混合检索；File Search 则把该检索能力作为模型可调用工具。具体字段和默认切分参数会变化，工程代码应锁定 API 版本并在升级时重新运行 Retrieval 与端到端 Evals，而不是把某一厂商默认值当作本章原理。
