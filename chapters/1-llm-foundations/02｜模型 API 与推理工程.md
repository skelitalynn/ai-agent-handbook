# 02｜模型 API 与推理工程

> 第 01 章解释模型内部如何完成训练与逐 Token 生成；本文把视角移到模型外部，建立从应用请求、远程推理、流式事件到类型化结果的完整调用链。学完后，读者应能实现一个不把厂商字段泄漏到业务层、能够处理状态、停止原因、Usage 和常见故障的模型客户端。Prompt 设计与输出 Schema 留到第 03 章，Tool Calling 留到第 05 章。

## 面试速记

### 背诵提纲

**1. 定义**

模型 API 是应用访问远程模型推理能力的协议接口；推理工程负责把不稳定、昂贵且具有概率性的模型调用封装成可配置、可观测、可恢复的系统组件。

**2. 完整调用链**

```text
业务请求 → 构造模型输入 → 发送 API 请求 → 服务端排队与推理
        → 接收完整响应或事件流 → 解析类型化结果 → 校验终态 → 记录 Usage 与 Trace
```

**3. 请求契约**

- **模型与版本**：模型标识决定能力、上下文、参数和价格边界，生产环境不能假设所有模型支持同一组参数。
- **输入**：输入通常由指令、消息和多模态内容块组成，厂商字段不同，但都要被序列化进本次推理上下文。
- **生成约束**：最大输出、停止条件、采样或推理强度控制计算与输出边界，不保证事实正确。

**4. 响应契约**

- **类型化输出**：响应不只有文本，还可能包含工具请求、拒绝、引用或其他内容块，业务层不能只读取一个字符串。
- **终止信息**：状态和停止原因用于区分自然完成、长度截断、工具调用、拒绝与错误。
- **Usage**：用量记录输入、输出、缓存或推理相关 Token，是成本、容量和回归分析的基础。

**5. 状态管理**

- **客户端管理**：应用保存并重传所需历史，控制力强，但必须自行处理裁剪、持久化和并发一致性。
- **服务端管理**：应用通过响应 ID 或会话对象延续上下文，调用更方便，但不等于获得长期记忆，也不必然减少上下文占用和计费。

**6. Streaming**

Streaming 通常通过 SSE 等传输返回类型化事件；客户端必须按事件类型增量组装结果，并以完成或错误事件判断终态，不能把每个数据块都当成文本 Token。

**7. 延迟、用量与限流**

- **延迟**：首 Token 延迟衡量多久开始看到结果，总延迟衡量请求何时真正完成；Streaming 主要改善首屏体验，不会自动减少生成计算。
- **限流**：服务可能同时限制请求数、输入 Token、输出 Token 或并发量，失败请求也可能占用限额。

**8. 错误与重试**

参数和权限错误应直接修复，网络错误、限流和部分服务端错误才适合在重试预算内指数退避；流中断后的部分输出不是成功结果，盲目重试还可能造成重复成本或副作用。

**9. 模型选择与版本**

先用真实任务评测确定质量达标的模型，再优化延迟和成本；生产环境应显式记录模型版本、参数和 Prompt 版本，并在切换模型或别名前执行回归评测。

### 高频对比

| 维度 | 非流式调用 | 流式调用 |
|---|---|---|
| 返回方式 | 完成后一次返回完整对象 | 逐步返回事件 |
| 首屏体验 | 必须等待完整生成 | 可较早展示增量结果 |
| 客户端复杂度 | 较低 | 需要事件状态机、增量组装和中断处理 |
| 完成判断 | HTTP 成功且响应对象有效 | 必须收到明确终态事件 |
| 适用场景 | 短输出、后台任务、严格原子处理 | 长输出、交互界面、需要进度反馈 |

| 维度 | 客户端管理上下文 | 服务端管理上下文 |
|---|---|---|
| 历史传递 | 应用显式重传 | 通过响应 ID 或会话引用 |
| 可移植性 | 较强 | 依赖厂商对象与保留策略 |
| 数据控制 | 应用可精确裁剪和持久化 | 需要理解服务端存储与合规语义 |
| 上下文成本 | 历史仍进入模型上下文 | 引用历史通常也不等于免费上下文 |

### 高频问题

#### 问题1：为什么 HTTP 200 或收到文本，还不能说明模型调用成功？

流式连接可能在返回 200 后发生错误，非流式结果也可能因长度上限、拒绝或工具请求而未形成最终答案。客户端应同时检查事件终态、响应状态、停止原因和输出类型。

#### 问题2：为什么 Streaming 通常不能降低完整回答的生成时间？

Streaming 改变的是结果传输和消费方式，使客户端更早收到增量内容；模型仍需执行相同的 Prefill 和逐 Token Decode。它主要降低感知等待和首 Token 延迟，不等于减少总计算量。

#### 问题3：如何判断一个模型 API 错误是否应该重试？

先按失败层级和错误类型分类：无效参数、认证和权限错误通常不可重试，限流、连接失败和临时服务端错误可以在 `Retry-After` 与重试预算约束下退避重试。若请求可能已经产生外部副作用，还必须先解决幂等问题。

#### 问题4：使用 `previous_response_id` 或 Conversation 后，为什么仍要管理上下文预算？

这些机制简化了历史传递，不改变模型只能在有限上下文中计算的事实。历史内容仍可能占用上下文并产生输入用量，应用仍需决定保留、压缩、检索或丢弃哪些信息。

#### 问题5：为什么不能直接选择排行榜最高或上下文最大的模型？

排行榜任务与真实业务分布可能不同，上下文容量也不代表目标任务质量。应先用真实 Prompt、数据和失败样本建立质量门槛，再在达标候选中比较延迟、成本、可用区、合规和版本稳定性。

## 1. 先看全程：一次模型调用怎样得到可用结果

假设运维页面要“把一条故障记录总结成三点”。页面需要尽快显示文字，但只有在回答完整、确实包含三点且没有被截断时，才能把它保存为正式摘要。最简单的代码看起来只是传入文本、取回字符串，生产调用却还要回答：请求怎样表达，流式内容怎样组装，什么状态才算完成，失败能否重试。

本章承接第 01 章的 Prefill、Decode 和停止条件，不再展开模型内部计算。学完后，读者应能把厂商提供的软件开发工具包（SDK）包在一个稳定客户端后面，让业务只接收明确的结果或错误，并能用终态、Usage、延迟和请求 ID 解释一次调用发生了什么。

```text
业务输入
   ↓ 构造内部请求
模型、输入、生成边界、状态策略
   ↓ 厂商适配器
SDK / HTTP 请求
   ↓ 远程模型服务
排队 → Prefill → Decode
   ↓
完整响应，或连续的流式事件
   ↓ 客户端组装与判断
类型化结果 / 类型化错误
   ↓
业务校验 + Usage、延迟、请求 ID 记录
```

这条链上有三种不确定性：模型可能生成不合格内容，网络或服务可能失败，模型和 API 版本还会变化。推理工程的任务，就是把这些不确定性收在一个可观察、可测试的客户端里，而不是让它们散落到业务代码中。

模型 API 只是远程推理的服务边界，不是模型本身。应用通常看不到 GPU 调度和 KV Cache，只能控制请求、读取事件并判断结果。第 01 章讲“模型内部怎样生成”，本章讲“应用怎样可靠地使用这次生成”。

## 2. 发送前：先把业务意图变成明确请求

### 2.1 业务层使用稳定类型，适配器负责厂商字段

如果运维页面直接构造某个 SDK 的请求对象，模型字段、消息格式和异常类型就会渗入业务代码。换模型或升级 API 时，摘要逻辑也要跟着修改。

业务层真正关心的是“故障记录是什么、要三点摘要、预算多少”，而不是某个 SDK 的类名。应用可以先定义稳定的内部请求，再由适配器转换成 OpenAI、Anthropic 或其他厂商的对象。

```text
业务 / Agent
   ↓ 统一的 ModelRequest
模型客户端
   ↓ 厂商字段映射、认证、序列化
OpenAI / Anthropic / 其他服务
```

一个请求通常包含：

| 信息 | 解决什么问题 |
|---|---|
| 模型标识 | 选择能力、版本和成本边界 |
| 输入内容 | 提供文本、消息或多模态内容块 |
| 指令 | 说明任务、角色和限制 |
| 生成边界 | 限制最大输出、停止条件或推理强度 |
| 能力声明 | 提供工具、输出 Schema 或所需模态 |
| 调用元数据 | 关联会话、实验版本和 Trace |

不要把所有厂商压成一个 `generate(prompt) -> str`。这种接口虽然短，却会丢失工具调用、拒绝、停止原因、Usage 和请求 ID。合适的抽象应统一稳定语义，同时允许显式表达厂商特有能力。

SDK 仍然有价值，它负责认证、序列化和部分协议细节；但它不知道“三点摘要”怎样才算业务成功，也不知道本次调用允许花费多少时间和 Token。这部分职责属于应用自己的模型客户端。

### 2.2 先检查模型能力，再发送参数

同一厂商的不同模型，也不一定支持相同的上下文长度、输入模态、工具、输出格式和生成参数。客户端应根据模型与版本检查能力，而不是维护一份“所有模型通用”的参数字典。

如果能力不匹配，应在发送前给出清楚错误。例如，摘要页面要求流式返回和固定结构，所选模型或接口却不支持对应能力，这不是网络故障，也不应该进入重试。通过检查后，故障记录才会被适配器转换成厂商请求并发送。

### 2.3 多轮对话必须明确由谁保存状态

模型每次推理只使用本次可见 Context。多轮对话只有两种基本做法：

| 方式 | 怎样继续下一轮 | 主要取舍 |
|---|---|---|
| 客户端管理 | 应用保存并重传所需历史 | 控制和迁移更容易，但要自行裁剪、持久化和处理并发 |
| 服务端管理 | 通过响应 ID 或会话对象引用历史 | 调用方便，但依赖厂商的存储与保留语义 |

OpenAI Responses API 可以通过 `previous_response_id` 或 Conversation 延续状态；Anthropic Messages 的基础方式由客户端提交历史消息。无论使用哪种方式，模型都仍受 Context Window 限制。引用历史不等于永久 Memory，也不保证历史不占用输入用量。

因此，客户端至少要回答：权威历史存在哪里、并发请求如何排序、哪些数据允许由厂商保存、历史何时裁剪或压缩。具体的 Context Engineering、Session 和 Checkpoint 会在后续章节展开。

到这里，业务意图已经变成了一次可发送的请求，状态归属也已经明确。下一步不能直接“取字符串”，而要先理解服务返回的是哪些对象和事件。

## 3. 返回时：先组装协议，再判断业务是否成功

### 3.1 响应是类型化对象，不只是文本

模型可能返回文本、工具请求、拒绝、引用或其他内容块。一个稳定的内部结果至少应保留：

```python
@dataclass(frozen=True)
class ModelResult:
    text: str
    finish_reason: FinishReason
    usage: Usage
    request_id: str
    model: str
```

这只是本章示例所需的最小结果。若业务支持工具或多模态输出，应增加明确的联合类型，而不是把非文本结果强行塞进字符串。

OpenAI Responses API 使用不同类型的 output items；Anthropic Messages API 使用不同类型的 content blocks。字段不同，但共同原则相同：先识别输出类型，再交给对应处理逻辑。

对故障摘要来说，三点文字只是结果的一部分。客户端还要保留它为何停止、实际使用哪个模型、消耗多少 Token，以及出现问题时用于厂商排查的请求 ID。

### 3.2 Streaming 是事件序列，不是字符串分片

非流式调用在生成结束后一次返回完整对象。Streaming 会在生成过程中持续发送事件，常见传输方式是 SSE。它能让界面更早显示内容，但不会让模型少做 Prefill 或 Decode，所以通常只改善感知等待，不保证缩短完整生成时间。

运维页面可以在收到文本增量后逐步显示三点摘要，但此时显示的是预览，不是可以保存的正式结果。只有收到完成事件并通过后续检查，页面才应提交摘要。

```text
START
   ↓ 创建事件
STREAMING
   ├── 文本增量 ───────┐
   ├── 结构化增量 ─────┤→ 按类型组装
   ├── Usage / 元数据 ─┘
   ├── 完成事件 → COMPLETED
   ├── 错误事件 → FAILED
   └── 断流/超时 → INDETERMINATE
```

事件、网络 chunk 和模型 Token 是三种不同边界。一次事件可能携带一段文本、结构化增量或元数据；一个 Token 也未必正好对应一个可显示字符。客户端必须按事件类型处理。

`INDETERMINATE` 表示客户端没有收到明确终态。即使已经显示了部分文本，也不能默认任务成功；最终 Usage、停止原因或结构化内容可能仍不完整。用户取消也应记录为取消，而不是成功。

如果下游处理速度低于事件到达速度，还要限制缓冲区或取消请求。这就是 Backpressure：避免生产者持续写入，而消费者来不及处理时无限占用内存。

### 3.3 只有明确终态才能提交结果

判断顺序应从协议完整性走向业务正确性：

```text
是否收到协议终态？
   ├── 否 → 标记失败或终态不确定
   └── 是
        ↓
响应状态是否完成？
   ├── 否 → 按失败、取消等状态处理
   └── 是
        ↓
停止原因和输出类型是否符合本次任务？
   ├── 否 → 进入工具、拒绝、截断等分支
   └── 是
        ↓
业务 Schema 与规则是否通过？
   ├── 否 → 语义失败
   └── 是 → 提交成功结果
```

| 信号 | 常见含义 | 客户端动作 |
|---|---|---|
| 自然完成 | 本轮正常结束 | 继续做类型和业务校验 |
| 达到最大输出 | 内容可能被截断 | 不静默当作完整答案 |
| 工具调用 | 模型请求外部能力 | 交给 Agent Loop，不当作最终文本 |
| 拒绝 | 模型或安全策略拒绝 | 保留原因并按产品策略处理 |
| 断流或流内错误 | 没有可靠终态 | 丢弃“完整成功”标记，再决定是否重试 |

HTTP 200 只说明服务器接受并开始返回响应，不一定说明任务最终完成。反过来，拿到一段看似完整的文本，也不能替代终态、停止原因和业务校验。

例如，页面已经显示了前两点后连接中断，这仍然是终态不确定，而不是“基本完成”。客户端可以保留预览用于提示用户，但不能把两点内容写入正式摘要字段。

### 3.4 Usage 和延迟用于成本控制，也用于诊断

Usage 可能包含输入、输出、缓存或推理相关 Token。它不只用于结算：输入 Token 突增，可能是重复历史或工具结果过大；输出经常顶到上限，可能是最大输出太小，也可能是任务没有明确收敛边界。

延迟至少分开记录：

- 连接或排队时间；
- 首事件或首 Token 延迟；
- 完整响应延迟。

只记录总耗时，会混淆“服务迟迟没有开始”和“回答太长导致 Decode 很慢”。单价容易变化，应把 Usage 事实和可更新的价格表分开保存，不要把长期价格硬编码进客户端。

对贯穿案例，可以分别观察“多久出现第一点”和“多久完成三点”。前者影响页面感知，后者决定任务何时真正完成；如果输入 Token 突然增长，还应检查是否把同一份故障记录或历史重复发送了。

到这里，流式事件已经被组装成明确终态，结果与可观测数据也已经分开。接下来只在失败确实可能自行恢复时重试，而不是把所有错误再次发给模型。

## 4. 失败时：先分类，再决定重试

重试只适合“同一请求稍后再执行可能成功”的情况。它不是所有异常的默认处理。

| 失败类型 | 例子 | 默认动作 |
|---|---|---|
| 请求无效 | 字段错误、Context 过长、参数不支持 | 修复请求，不重试 |
| 认证或权限 | API Key 无效、模型无访问权 | 修复配置或授权 |
| 配额或账单 | 额度耗尽、账户异常 | 告警并停止 |
| 限流 | 请求或 Token 速率超限 | 尊重 `Retry-After`，在预算内退避 |
| 临时服务故障 | 过载、部分 5xx | 带 Jitter 的指数退避 |
| 网络故障 | 连接失败、读取超时、断流 | 根据终态和幂等风险决定 |
| 语义失败 | 输出类型错误、内容不合格 | 校验、修复或重新规划，不等同于网络重试 |

同样是摘要失败，原因可能完全不同：故障记录超过 Context Window 要缩减输入，账户无额度要停止调用，临时过载才适合等待后重试，摘要不是三点则应进入输出校验或 Prompt 修正。先分类，是为了避免用网络重试掩盖确定性的设计错误。

### 4.1 重试必须受预算限制

指数退避让等待时间随尝试次数增加，Jitter 用随机扰动避免大量客户端同时重发。至少设置三项上限：最大尝试次数、最大累计等待时间、最大额外费用。失败请求也可能占用速率额度，立即无限重发只会让拥塞更严重。

HTTP 429 也不能只按状态码决定无限重试。它可能表示短时速率限制，也可能与配额或账户状态有关；客户端应读取错误类型和 `Retry-After`，再在总预算内决定是否继续。

超时也不要只设一个数字。连接超时限制“多久还没连上”，读取超时限制“多久没有新数据”，总截止时间限制“整个任务最多运行多久”。Streaming 能持续显示进度，但不能替代总截止时间和取消机制。

### 4.2 重放请求前先考虑幂等性

纯文本生成重试通常不会修改业务数据，但会重复计费，也可能得到不同输出。进入 Agent Loop 后，整段流程还可能已经发邮件、扣款或写数据库。若无法判断上次执行到哪一步，不能直接无限重放。

模型客户端至少应生成稳定请求标识、记录每次尝试及其终态。工具的副作用控制与幂等设计将在第 05 章进一步讨论。

## 5. 上线前：把选择标准和客户端行为固定下来

### 5.1 用评测选择模型并管理版本

模型选择的顺序应是：先满足质量和硬约束，再优化成本与延迟。

```text
定义真实任务与失败标准
   ↓
收集正常、困难、长输入和失败样本
   ↓
用相同 Prompt 与评分规则评测候选模型
   ↓
淘汰质量或能力不达标者
   ↓
在达标者中比较延迟、费用、限流和合规
```

排行榜只能帮助筛选候选，不能替代业务评测。上下文更长、参数更多或发布时间更新，也不自动表示更适合你的任务。

对故障摘要，质量门槛可以包括：是否准确覆盖原因、影响和处置，是否稳定输出三点，是否遗漏高风险信息。只有达到这些门槛的模型，才继续比较首点延迟、完整响应时间和 Token 成本。

工程选型还要检查：

- 是否支持所需模态、工具、结构化输出和上下文长度；
- P50、P95 首 Token 延迟与总延迟是否满足预算；
- 输入、输出、缓存和推理如何计费；
- 限流、区域、数据保留和合规要求是否满足部署条件；
- 是否提供固定快照、稳定版本或明确的弃用计划。

模型别名便于自动升级，但行为可能变化；固定快照更容易复现，却需要主动迁移。生产系统应把默认模型放进配置，记录实际模型版本，并在变更前跑回归评测。

至此，一次调用从请求构造、远程执行、事件组装、终态判断、失败处理走到了上线决策。最后用一个最小客户端验证其中最容易被业务代码忽略的协议边界。

### 5.2 用最小客户端验证整条链

本章示例位于 [`examples/02-model-api-inference/`](../../examples/02-model-api-inference/)。它不连接真实厂商，而是用模拟事件验证三条规则：只有终态事件才算完成；断流后的部分文本不能冒充成功；只有可重试错误才进入有预算的退避。

核心流组装器只关心协议状态：

```python
def collect_stream(events: Iterable[StreamEvent]) -> ModelResult:
    text_parts: list[str] = []
    for event in events:
        if isinstance(event, TextDelta):
            text_parts.append(event.text)
        elif isinstance(event, Completed):
            return ModelResult(
                "".join(text_parts),
                event.finish_reason,
                event.usage,
                event.request_id,
                event.model,
            )
        elif isinstance(event, Failed):
            raise InferenceError(event.code, event.message, event.retryable)
    raise IncompleteStreamError("stream ended without a terminal event")
```

真实适配器负责把厂商事件映射成 `TextDelta`、`Completed` 和 `Failed` 等内部类型。业务层只依据统一结果决策；新增厂商时，变化尽量留在适配器内。若厂商提供了内部类型尚未表达的能力，应显式扩展类型，不要静默丢弃。

截至 2026-07-22，OpenAI Responses API 与 Anthropic Messages API 的对象名称不同，但可以沿同一条调用链理解：

| 语义 | OpenAI Responses API | Anthropic Messages API |
|---|---|---|
| 输入 | 字符串或类型化 Items | 顶层 `system` 与 `messages` 内容块 |
| 输出 | 类型化 output Items | 类型化 content blocks |
| 多轮状态 | 重传 Items，或引用响应 / Conversation | 客户端提交历史轮次 |
| Streaming | 类型化 Response 事件 | 消息与内容块事件 |
| 终止信号 | Response 状态、事件和输出语义 | `stop_reason` 与最终消息事件 |
| 用量 | Response `usage` | Message `usage` |

不要把这张表当成永久字段清单。真正稳定的是五个问题：请求怎样表达、输出有哪些类型、终态怎样判断、历史由谁管理、错误与 Usage 怎样记录。学习新厂商 API 时，沿这五个问题映射即可。

示例刻意没有实现 Prompt Schema、工具循环、持久状态和完整 Trace。它们属于后续章节；把所有能力提前塞进一个客户端，只会掩盖本章要验证的远程调用边界。

这个示例也没有通过降低 Temperature 来宣称摘要“可靠”。第 01 章已经说明，Temperature 只改变候选 Token 的选择分布；本章的可靠性来自完整终态、结果校验、评测和故障处理。

## 学习检查

完成本章后，应当能够：

- 画出一次模型请求从业务输入到终态结果的完整生命周期；
- 设计能表达输出类型、停止原因、Usage、请求 ID 和错误分类的内部类型；
- 解释客户端状态与服务端状态的取舍，以及二者为何都受 Context Window 限制；
- 实现一个按类型组装事件、拒绝不完整流的最小 Streaming 客户端；
- 根据错误类型、终态、幂等风险和预算决定是否重试；
- 用真实任务评测而不是排行榜完成模型选型和版本升级。
