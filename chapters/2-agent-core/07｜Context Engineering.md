# Context Engineering

> 本文解释如何在每次模型调用前，把指令、工具、历史、运行状态和外部资料编排成有限且可验证的 Model Context。它承接第 06 章保存下来的 State，并为后续 Evals、RAG 与 Memory 提供统一的输入边界。

## 面试速记

### 背诵提纲

**1. 定义**

Context Engineering 是在每次模型推理前，对完整输入信息进行收集、选择、排序、压缩、隔离和预算控制，使有限 Token 尽可能支持当前决策。

**2. Context 组成**

Model Context 通常包含系统与开发者指令、工具定义、当前请求、必要历史、运行状态、检索或 Memory 结果，以及工具返回；代码侧 Runtime Context 不会天然被模型看到。

**3. 完整编排链路**

```text
收集候选 → 权限与新鲜度过滤 → 去重和选择 → 必要时压缩
         → 排序与边界标记 → 精确计数 → 调用模型 → 记录效果
```

**4. Token 预算**

输入预算应从模型窗口中预留期望输出和安全余量；必选信息放不下时应显式失败或切换策略，不能静默删掉指令、当前请求或关键约束。

**5. 选择策略**

选择同时考虑任务相关性、必要性、新鲜度、可信度、信息增益和 Token 成本；Context Window 是容量上限，不是必须填满的目标。

**6. 顺序与结构**

指令层次、消息角色和 Tool Call/Result 配对必须保持；稳定前缀有利于 Prompt Cache，动态内容放后，但缓存优化不能破坏语义正确性。

**7. 压缩与跨窗口续作**

Compaction 用更少 Token 保留目标、已确认事实、关键决策、未完成项和证据引用；它是有损转换，必须保留可追溯来源并评测遗漏。

**8. 按需加载与隔离**

大文件和大结果应优先保留路径、索引和摘要，再通过工具按需读取；不相关子任务可使用独立上下文，避免中间过程污染主任务。

**9. 失败与评测**

常见失败包括 Context 缺失、污染、冲突、过期、溢出和压缩失真；应记录每轮选入与省略内容、Token 分布和来源版本，并用长度、位置和干扰项测试验证。

### 高频对比

| 维度 | Truncation（截断） | Compaction（压缩） |
| --- | --- | --- |
| 机制 | 按长度直接移除 Item 或 Token | 重写为更短的结构化状态或摘要 |
| 优点 | 快、确定、成本低 | 更可能保留跨轮语义和未完成事项 |
| 主要风险 | 机械删除关键前因 | 摘要遗漏、误写或失去原始证据 |
| 适合内容 | 可证明不再需要的旧原始输出 | 仍需延续但过长的任务轨迹 |

### 高频问题

#### 问题1：模型窗口足够大时，为什么不能把所有信息都放进去？

更长输入会增加成本和延迟，也会引入无关信息、冲突与位置敏感性。窗口能容纳只说明请求合法，不证明模型能稳定找到并使用其中每条信息。

#### 问题2：必选信息已经超过输入预算时应该怎么办？

不能静默删除安全约束或当前请求。应减少非必选内容、先对历史或资料做可验证压缩、拆分任务或改用更大窗口；仍无法满足时应明确拒绝本轮调用。

#### 问题3：如何判断 Compaction 是否丢掉了关键内容？

用真实长轨迹建立保留项清单，分别测量关键事实、决策、未完成项和证据引用的 Recall，再评估冗余和成本。还要测试多次连续压缩，因为误差会跨轮累积。

#### 问题4：如何判断失败来自模型能力还是 Context 编排？

固定模型和解码设置，对照运行完整 Oracle Context、当前 Context 与删除单一来源后的版本。如果 Oracle 成功而当前版本失败，应先检查召回、排序、冲突、截断和压缩链路。

#### 问题5：检索文档或工具结果中包含指令时，为什么加标签仍不够？

标签只提供语义提示，不能形成安全边界。系统还需按来源隔离不可信数据、限制工具权限、验证输出和高风险动作，并在 Evals 中加入 Prompt Injection 样本。

## 1. 先看完整输入：Context 是每次调用重新编译的结果

最重要的心智模型是：Model Context 不是数据库，也不是 Session 的别名，而是 Runtime 为某一次模型调用编译出来的 Token 序列。同一个 Run 的下一步目标不同，应该看到的 Context 也可能不同。

继续使用前两章的订单任务。Run 42 已从 Checkpoint 恢复，用户批准了取消 A-17。Runtime 应先按第 06 章的恢复协议执行与审批完全一致的动作，而不是让模型重新改写参数。假设工具随后返回“取消成功，订单 revision=10”，系统需要再次调用模型解释结果并判断是否还有后续事项。这次调用不应接收“数据库里能找到的所有内容”，而应看到足以完成当前步骤的最小高信号集合：

```text
候选信息
  受控 Policy：旧批准不能授权新的动作                ─┐
  Checkpoint v5：cancel_order 已完成，含操作 ID       ┤
  审批记录：approved，绑定 call_id 与参数摘要         ┤
  最新订单状态：A-17 已取消，revision = 10            ┤
  Tool Result：cancel_order 成功，绑定原 call_id      ├→ Context Builder
  下一步确有需要时才加入的 Tool Definition            ┤
  Session History：用户此前的说明与修正              ┤      │
  旧订单状态：仍可取消，revision = 9                  ┤      ├─ 权限与版本过滤
  历史闲聊、完整工具日志                              ┤      ├─ 必选与可选分类
  外部文档与 Memory 候选                             ┘      ├─ 预算选择与压缩
                                                           ├─ 排序与信任边界
                                                           └─ 最终 Token 计数
                                                                  ↓
                                                           Model Context
                                                                  ↓
                                                               模型调用
                                                                  ↓
                                                     Usage、Context Manifest、Trace
```

在这张图中，State、历史、工具结果和外部资料都只是候选来源。只有通过 Builder 选择并渲染的部分才会成为 Model Context。旧 revision、无关闲聊和超大日志即使仍被持久化，也不应自动进入本轮输入。

第 03 章的 Prompt Engineering 主要解决指令怎样表达、示例怎样组织和输出怎样约束。Context Engineering 的范围更大：哪些指令版本生效、暴露哪些工具、携带多少历史、检索哪些资料、是否压缩旧轨迹，以及各部分如何在预算内组合。Prompt 是 Context 的组成部分，两者不是互斥方案。

工程语境中的 `context` 经常重载。OpenAI Agents SDK 就明确区分两种对象：本地 Runtime Context 可以保存依赖、用户 ID 和代码侧状态，但不会自动发给 LLM；Model Context 才是模型生成时能够读取的输入。看到某个框架的 `context` 参数时，必须先确认它属于哪一层。

## 2. 第一步：从 State 与外部来源收集候选信息

Context Builder 不应该只是字符串拼接函数。它需要把信息供给变成一条可观察、可回归的流水线：

```text
1. 收集候选
   ↓
2. 校验身份、权限、来源和版本
   ↓
3. 规范化、去重并解决冲突
   ↓
4. 标记必选项，给可选项评分
   ↓
5. 在预算内选择；必要时压缩或按需加载
   ↓
6. 按指令层次和消息协议排序、渲染
   ↓
7. 使用目标模型 Tokenizer 重新计数
   ├── 超预算 → 重新选择、压缩、拆分或失败
   └── 合法   → 调用模型并记录 Context Manifest
```

候选信息可能来自不同信任域。系统策略来自受控配置，用户消息来自当前主体，检索文档来自知识库，网页和工具返回则可能完全不可信。Builder 在选择前就要完成权限过滤，不能先把越权数据交给模型，再要求模型“不要使用”。

规范化阶段要解决同一事实的多个版本。例如订单状态同时出现 `pending` 和 `cancelled` 时，仅靠相关性评分可能把两者都选入。系统应依据业务版本、时间戳或权威来源先确定有效事实；无法自动解决时，把冲突显式呈现给决策逻辑，而不是悄悄任选一个。

放回贯穿案例里，`订单 A-17 当前版本 revision=10` 应覆盖执行前的 `revision=9`；当前策略、与原 `call_id` 关联的 Tool Result、已完成步骤和最新订单状态应标记为必选项，而更早的解释性对话只能作为可选项。已经用过的 `cancel_order` 定义如果不再服务于下一步，也不必因为它存在于 Tool Registry 就继续占用 Context。这里不是简单地把旧信息全部删除，而是先决定它们有没有资格参与本次构建。

### 2.1 Context Manifest 记录选入和省略的原因

建议为每次调用记录一个 Context Manifest，而不必把所有敏感原文复制进 Trace。它至少包含：

- Item ID、类型、来源、版本和可信级别；
- 是否必选、选择分数与被选中或省略的原因；
- 每一部分的 Token 数、总输入预算和输出预留；
- 使用的压缩器、摘要版本及原始 Artifact 引用；
- Prompt、工具集合、模型和 Context Builder 的版本。

最终答案错了时，Manifest 可以先回答“模型是否看到过正确证据”。没有这层记录，团队很容易把检索遗漏、旧版本冲突或机械截断误判成模型能力问题。

例如，A-17 这次构建的 Manifest 应能回答：为什么 `order:A-17@10` 被选中、为什么 `order:A-17@9` 因版本陈旧被丢弃、为什么执行结果必须与原 `call_id` 一起保留，以及某段旧会话为何因为预算不足被省略。

## 3. 第二步：先保护必选项，再让可选信息竞争预算

设模型支持的总窗口为 `W`，本轮输入为 `I`，预留输出为 `O`，实现保留的安全余量为 `R`，则 Builder 的基本约束是：

```text
I + O + R ≤ W
```

不同 API 对工具定义、图像、音频、推理 Token 和最大输出的计量规则并不完全相同，因此生产系统应使用目标模型和当前 API 的官方 Tokenizer 或计数接口，不能长期依赖“一个汉字约等于一个 Token”之类经验值。预算还要包含消息包装、工具 Schema 和系统自动注入内容，而不只是肉眼可见的正文。

合理的预算顺序是先保留不可妥协项，再竞争剩余空间：

1. 安全与行为边界、当前任务、必要输出约束；
2. 当前步骤必须依赖的业务事实和工具协议；
3. 与问题直接相关的证据、近期历史和错误反馈；
4. 可提升质量但缺失后仍能工作的背景信息。

必选项本身超出预算时，Builder 应返回结构化错误。静默从头或从尾删除最危险，因为被删除的可能恰好是系统策略或当前用户修正。此时可选择压缩非必选区、拆成多个阶段、改为按需读取，或在产品允许时切换更大窗口模型。

对 A-17 这次“解释取消结果”的调用而言，当前策略、当前用户请求、Checkpoint 中的已完成步骤、与原调用关联的结果和订单最新版本都属于必选项。旧的解释性对话、历史查询结果、已经不需要的工具定义和调试日志可以作为可选项或直接淘汰。这样即使预算紧张，模型仍然知道“刚才实际发生了什么”，而不是只保留一些主题相近却已经过期的背景。

窗口也不应被视为填充指标。`Lost in the Middle` 论文在其评测的多文档问答和键值检索任务上观察到明显的位置敏感性，相关信息位于中部时常表现更差；扩展窗口模型也不必然更善于使用窗口内信息。这一结果来自特定时期的模型与任务，不能机械外推到所有新模型，但它给出了正确的验证方法：对目标模型改变长度、相关信息位置和干扰项数量，而不是只测“能否提交长请求”。

### 3.1 选择不能只看相似度

相关性只是 Context 选择的一项信号。一个候选 Item 的工程价值通常还取决于：

| 信号 | 要回答的问题 |
| --- | --- |
| 必要性 | 缺少它是否会违反约束或无法完成当前步骤？ |
| 相关性 | 它是否直接支持当前决策，而非只与主题相似？ |
| 新鲜度 | 它是否已被更新版本替代？ |
| 权威性 | 它来自业务真源、用户陈述还是未经验证网页？ |
| 信息增益 | 它是否只是重复已有内容？ |
| Token 成本 | 它带来的收益是否值得占用窗口？ |

简单系统可以使用规则和加权分数；高风险系统则常把权限、必选约束和冲突处理做成硬门槛，再对剩余候选排序。不能让一个高相似度但越权的文档越过权限过滤，也不能让十份重复资料挤掉唯一的反例。

第 10 章会详细讨论检索召回、重排和引用。对本章而言，RAG 输出只是候选信息的一种来源：检索器负责找到可能相关的片段，Context Builder 仍负责与指令、历史和预算一起完成最终选择。

完成资格过滤和预算选择后，还不能直接把条目随意拼接起来：同一批内容的排列方式会影响模型能否正确理解约束，也会影响缓存是否命中。

### 3.2 排序必须先保证语义和协议，再考虑缓存

Context 不是无序集合。指令层次需要保持第 03 章定义的优先级，消息角色不能丢失，Tool Call 与对应 Tool Result 也要符合 API 的配对和顺序要求。将所有内容压成一段纯文本，可能破坏模型原生协议提供的边界。

在语义正确的前提下，可以把稳定的系统指令、工具定义和 Few-shot 示例放在共同前缀，把用户请求、实时状态和检索结果放在后部。OpenAI 当前 Prompt Caching 文档说明，缓存命中依赖精确前缀匹配，因此这种布局也有助于降低重复前缀的延迟和成本。

但“静态在前、动态在后”不是可以凌驾于语义的通用排序算法。某些模型对长 Context 的位置敏感，某些 API 要求工具消息紧邻对应调用；高优先级指令也不能为了缓存放进普通数据区。顺序应通过目标任务评测决定，缓存的 `cached_tokens` 等指标只证明复用发生，不能证明答案更正确。

## 4. 第三步：放不下时选择压缩、按需加载或隔离

当对话或 Agent 轨迹接近预算时，机械截断只能删除内容；Compaction（上下文压缩）则尝试把旧窗口转换成更短、可继续工作的状态。高质量压缩至少应保留：

- 当前目标、完成条件和用户后续修正；
- 已验证事实与其证据引用；
- 已做出的关键决策及理由；
- 已完成步骤、未完成项和已知失败；
- 外部副作用、操作 ID 与不可重复动作；
- 下一步所需文件、Artifact 或工具结果引用。

原始大段日志、重复工具输出、闲聊和已经被结构化状态吸收的中间文本通常是优先清理对象。与其让摘要声称“测试已通过”，更稳妥的做法是保留测试报告 Artifact 的引用、命令和时间，让需要时可以回查。

在 A-17 的完整轨迹中，压缩结果至少要保留：批准绑定的 `call_id` 与参数、订单最新版本、动作当前阶段、幂等键和外部操作 ID；如果结果仍未确认，还必须保留这一不确定性。寒暄、重复解释和大段调试输出可以省略。这样压缩后的 Context 仍能区分“已批准但未执行”“结果未知”和“已经取消成功”，而不是只剩“用户同意取消订单”这句含糊摘要。

压缩的两个核心指标存在张力：Recall 要求不要遗漏潜在关键项，Precision 要求不要把冗余全部搬进摘要。Anthropic 的官方工程文章建议先在复杂 Agent Trace 上保证关键内容召回，再逐步删除无关信息。压缩提示本身、输入范围和结果 Schema 都需要版本化；连续多次摘要还要专门测试事实漂移和错误累积。

OpenAI Responses API 当前提供两种具体 Compaction 路径：可在请求中设置阈值触发服务端压缩，也可显式调用独立压缩端点。其返回可能包含不面向人类解释的专用 Item，因此应用必须按照官方协议携带，而不能把所有厂商实现假设成普通文本摘要。厂商能力会变化，使用时应重新核对目标模型和接口文档。

### 4.1 大对象优先保留引用，再按需加载

代码仓库、长 PDF、数据库结果和完整日志通常不应在任务开始时全部进入 Context。更有效的模式是先提供轻量目录和稳定引用，再让 Agent 通过工具逐步读取：

```text
文件路径 / 文档标题 / 查询句柄 / Artifact ID
                   ↓
              模型判断缺口
                   ↓
          搜索、读取局部、查看元数据
                   ↓
           将必要片段加入下一轮 Context
```

这种 Progressive Disclosure（渐进披露）降低初始 Token 和无关信息，但会增加工具往返、延迟和搜索失败风险。适合经常变化或体量很大的信息；对每次都必需且很短的规则，直接放入稳定前缀更可靠。实际系统常采用混合方案：固定注入小型索引与关键约束，其余内容按需探索。

文件和 Artifact 也是跨窗口续作的载体。Agent 可以把计划、已确认决策和阶段结果写成结构化笔记，后续只加载摘要与当前相关文件。这里的笔记仍属于外部 State；只有被 Builder 选入时才成为 Model Context。

当压缩仍然放不下，系统才应把完整日志、长文档或历史工具结果留在外部存储，只把引用和定位信息放入 Context。接下来还要解决另一个独立问题：这些按需读取的外部内容可能并不可信。

隔离是另一种减少污染的方法：把边界明确的搜索或分析交给独立上下文，只把带来源的结果返回主流程。它可以避免海量中间日志占据主 Agent 的注意力，却引入协调成本、信息损失和新的失败边界。第 15 章会讨论何时值得使用 Multi-Agent；Context 不够整洁本身并不是盲目拆 Agent 的理由。

### 4.2 不可信内容进入 Context 后仍然只是数据

网页、邮件、用户上传文件和工具结果可能包含“忽略之前规则”之类文本。它们与系统指令共享 Token Window，但不应共享权威性。Builder 应保留来源和可信标签，使用 API 支持的角色或结构化字段表达边界，并避免把外部文本拼接到高优先级指令中。

纯文本标签或 XML 分隔符有助于模型理解，却不是权限隔离。真正的控制仍位于模型外部：工具只暴露最小权限，参数经过验证，高风险副作用需要策略检查或人工审批，模型输出不能直接成为 SQL、Shell 或业务授权。第 24 章会完整展开 Agent Security；本章只要求 Context Pipeline 不主动抹掉信任边界。

到这里，Builder 已经完成候选收集、资格过滤、预算选择、顺序编排和不可信数据隔离。下一步需要用一个可运行的最小实现验证：必选项是否真的不会被静默裁掉，可选项是否按规则竞争预算，以及构建结果是否暴露了基本取舍。

## 5. 用最小 Context Builder 验证预算与选择

仓库中的完整示例位于 [`examples/07-context-engineering/`](../../examples/07-context-engineering/)，用标准库实现了一个确定性选择器。调用方显式提供每个 Item 对最终渲染序列的 Token 成本，Builder 先扣除输出预留，再保留必选项，并按优先级与成本选择可选项。

核心决策可以压缩为：

```python
required_tokens = sum(item.tokens for item in required)
if required_tokens > self._input_budget:
    raise ContextBudgetError(
        f"required context uses {required_tokens} tokens, "
        f"input budget is {self._input_budget}"
    )

remaining = self._input_budget - required_tokens
selected_optional: list[ContextItem] = []
for item in sorted(
    optional,
    key=lambda value: (-value.priority, value.tokens, value.item_id),
):
    if item.tokens <= remaining:
        selected_optional.append(item)
        remaining -= item.tokens
```

示例还会按逻辑 ID 丢弃旧 Revision；同一 Revision 出现不同 Payload 时显式报错，而不是随机选取。渲染顺序固定为稳定指令、参考信息、历史、工具结果和当前用户输入，不可信内容带有可见边界。返回值同时暴露 `used_tokens`、`input_budget` 和 `omitted_item_ids`，便于写入 Trace。

这只是验证 Context 编排机制的教学实现，不是通用最优选择算法。它没有计算语义相关性，也没有处理原生消息与 Tool Item 协议；显式 Token 数必须由生产调用方使用目标模型计数后提供，并包括边界包装开销。8 个单元测试分别覆盖输出预留、必选项保护、超预算失败、优先级、版本去重、冲突拒绝、不可信数据边界和稳定顺序。

## 6. 用 Context Manifest 和对照实验定位失败

Context Engineering 的质量不能只看平均 Token 数。至少需要以下几类指标：

- **预算指标**：输入 Token、输出预留、各来源占比、溢出与压缩频率；
- **选择指标**：关键证据 Recall、无关内容比例、旧版本和冲突率；
- **效果指标**：任务成功率、引用正确率、工具选择与参数正确率；
- **工程指标**：首 Token 延迟、总延迟、缓存命中、检索和压缩成本；
- **安全指标**：越权资料进入率、Prompt Injection 成功率和高风险动作拦截率。

定位时使用消融实验比调 Prompt 更有效。固定模型、温度和任务样本，分别运行：只含必要信息的 Oracle Context、生产 Builder 输出、加入干扰项的版本、改变证据位置的版本，以及压缩前后的版本。如果生产版本失败而 Oracle 成功，问题更可能位于选择或编排；两者都失败时，再考虑模型能力、任务定义或工具设计。

完成本章后，单 Agent 已经具备模型调用、工具、可恢复 State 和受预算约束的 Context。下一篇开始建立 Agent Evals，用可重复数据证明这些组件在任务、故障和版本变化下是否真正有效。

## 学习检查

完成本章后，应能：

- 画出 State、候选来源、Context Builder、Model Context 与模型调用之间的位置关系；
- 解释为什么数据库、Session History 和 Runtime Context 中的信息不会自动成为 Model Context；
- 为 `cancel_order(A-17)` 恢复并执行后的下一次模型调用区分必选项、可选项、陈旧项和不可信项；
- 使用输出预留和安全余量计算输入预算，并在必选项超预算时显式失败；
- 结合必要性、相关性、新鲜度、权威性、信息增益和 Token 成本选择候选内容；
- 在不破坏指令层次与 Tool Call/Result 协议的前提下优化顺序和缓存；
- 判断何时采用 Compaction、按需加载或独立上下文，并说明各自损失；
- 使用 Context Manifest、Oracle Context、干扰项和位置对照实验定位编排故障。
