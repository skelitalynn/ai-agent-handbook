# Agent Evals

> 本文建立 Agent 的评测闭环：把产品目标转换成 Task、Trial、Outcome、Trace 和 Grader，并用重复运行与回归门禁判断一次改动是否真正有效。它位于 RAG、Memory 和复杂编排之前，使后续新增能力都有可比较的质量基线。

## 面试速记

### 背诵提纲

**1. 定义**

Agent Eval 是针对完整 Agent 系统的可重复实验，用预先定义的任务、环境和评分标准衡量结果正确性、行为合规性、稳定性及资源消耗。

**2. 核心对象**

Task 是带输入和成功标准的测试用例，Trial 是一次实际尝试，Trace 是执行轨迹，Outcome 是环境终态，Grader 是评分逻辑，Eval Harness 负责运行、记录和聚合。

**3. 完整评测链路**

```text
定义成功 → 构造数据集与环境 → 运行多个 Trial → 评分 Outcome 与 Trace
         → 分层聚合和误差分析 → 与基线比较 → 阻断回归或发布
```

**4. 评测层次**

优先验证真实 Outcome，再检查最终输出、工具选择与参数、策略约束、步骤、延迟和成本；最终答案正确不能掩盖危险或偶然的执行路径。

**5. Grader 类型**

代码评分器便宜、稳定但可能僵硬，模型评分器能处理开放答案但有偏差和随机性，人工评分质量高但昂贵；实际系统通常组合使用并用人工样本校准自动评分。

**6. 数据集设计**

数据应覆盖正常、模糊、异常、安全和历史故障，并按场景与风险分层；开发集用于迭代，保留集用于发布判断，生产失败应持续回流但要去重和脱敏。

**7. 非确定性指标**

`pass@k` 衡量 k 次 Trial 至少一次成功，适合允许多候选的任务；`pass^k` 衡量 k 次全部成功，适合要求每次可靠的用户路径，不能用前者掩盖不稳定。

**8. 能力与回归**

Capability Eval 探索当前能力边界，Regression Eval 保护已经稳定的行为；能力项成熟后应晋升为高通过率回归项并进入持续评测。

**9. 版本与门禁**

每个结果必须绑定模型、Prompt、Tool、Context、Runtime、数据集和 Grader 版本；安全与高风险失败应设置独立硬门禁，不能被平均质量分抵消。

### 高频对比

| 维度 | Capability Eval | Regression Eval |
| --- | --- | --- |
| 核心问题 | Agent 现在能做到什么、边界在哪里 | 已经会做的事情是否退化 |
| 用例难度 | 有意包含当前难题，初始通过率可较低 | 已验证可通过，预期长期稳定 |
| 主要用途 | 研究改进方向和能力上限 | CI、模型升级和发布门禁 |
| 维护方式 | 解决后可晋升为回归项 | 一旦失效就定位变更或修正失真的用例 |

### 高频问题

#### 问题1：最终答案正确时，为什么还要评测 Trace？

Agent 可能通过越权工具、错误参数或重复副作用偶然得到正确答案。Outcome 判断是否完成，Trace Grader 判断过程是否合规并帮助定位原因，两者不能相互替代。

#### 问题2：如何证明 LLM-as-a-Judge 可以信任？

先写具体 Rubric 和少量带专家标签的校准集，测量模型评分与人工评分的混淆和一致性，并持续抽检分歧样本。高风险硬约束仍应优先使用代码或环境验证。

#### 问题3：为什么 `pass@5` 很高，用户仍然可能觉得产品不可靠？

`pass@5` 只要求五次中至少一次成功，可能掩盖单次体验很差。面向用户的一次性操作应重点看 `pass@1`、Trial 成功率或 `pass^k`，并单独报告尾部场景。

#### 问题4：离线 Eval 提升但线上指标下降，应该检查什么？

检查数据分布、环境真实性、工具与权限版本、评分器偏差、样本泄漏和线上交互反馈。离线任务若不能复现真实约束，分数只证明对该测试集有效。

#### 问题5：如何避免团队为了 Eval 分数过拟合？

分离开发集与保留集，限制查看保留答案，定期加入新生产失败和对抗样本，并保留人工盲测。修改评分器或任务定义时要版本化，不能悄悄改口径制造提升。

## 评测对象是完整系统，而不只是模型

Agent 的输出由模型、Prompt、工具、Context、Runtime、环境状态和采样共同决定。只比较两个模型在静态问答上的准确率，无法回答“订单是否真的取消”“是否调用了越权工具”或“失败后是否重复扣款”。Agent Eval 必须把这套组合看成被测系统。

```text
模型 + Prompt + Tool + Context + Runtime + Environment
                         │
                         ↓
                    Agent Trial
                         │
              ┌──────────┴──────────┐
              ↓                     ↓
          Trace / 输出          Environment Outcome
              │                     │
              └──────────┬──────────┘
                         ↓
                      Graders
```

这也解释了为什么 Evals 被放在 RAG、Memory、Planning 和 Multi-Agent 之前。之后每增加一个数据源、控制策略或 Agent，系统自由度都会上升；如果没有现成的任务集和基线，就无法区分能力提升、成本转移和隐蔽回归。

Eval 不是普通单元测试的替代物。确定性代码仍应使用单元测试验证 Schema、权限和状态转换；Agent Eval 则把这些检查放进真实任务轨迹，测量概率系统能否在环境中稳定满足目标。

## Task、Trial、Trace 与 Outcome

一个可复现的评测需要先把对象定义清楚：

| 对象 | 含义 | 必要内容 |
| --- | --- | --- |
| Task | 一个测试问题 | 初始输入、环境、成功标准、标签和风险级别 |
| Trial | 对 Task 的一次尝试 | 运行配置、随机性、最终输出和执行结果 |
| Trace | Trial 的执行记录 | 模型调用、工具调用、参数、结果、错误和状态变化 |
| Outcome | Trial 结束后的外部结果 | 数据库、文件、页面或其他业务真源状态 |
| Grader | 对某一方面评分的逻辑 | 输入范围、Rubric、阈值和解释 |
| Eval Harness | 端到端运行设施 | 环境重置、并发、记录、评分和聚合 |

Outcome 与 Agent 的自述尤其容易混淆。Agent 输出“航班已经预订”只是文本；预订记录实际存在、旅客和日期正确、没有重复扣款，才是环境 Outcome。能直接查询业务状态时，应优先以它为真源。

Trace 用于回答为什么成功或失败。例如最终订单状态正确，但 Trace 显示 Agent 先取消错误订单又补偿回来，这个 Trial 仍可能违反策略或制造不可接受风险。相反，强制唯一工具序列也可能误杀同样安全有效的新路径，因此 Trace Grader 应检查必要约束，而不是把参考轨迹当成唯一答案。

模型的隐藏推理过程不是稳定、完整的外部接口。评测应聚焦可观察的模型输出、工具决策、状态变化和证据，不要求模型暴露或匹配某段预设 Chain-of-Thought。

## 从产品要求反推成功标准

一个好的 Eval 从产品不变量开始，而不是先选流行 Benchmark。以“取消订单 Agent”为例，成功至少可能包含：

- 目标订单最终处于 `cancelled`；
- 只能取消属于当前用户的订单；
- 已发货订单必须拒绝或转人工；
- `cancel_order` 参数必须使用正确订单 ID；
- 不得调用 `issue_refund`，除非退款条件成立；
- 整个任务在步数、延迟和成本预算内结束；
- 最终回复准确说明实际 Outcome，不虚构成功。

这些条件的风险不同。一个措辞略差可以降低质量分，越权取消则必须让 Trial 失败。把全部维度加权成单一平均分可能出现“文风优秀抵消安全违规”的荒谬结果，因此硬约束与软质量应该分层聚合。

```text
硬门禁：权限、政策、不可逆副作用、数据泄露
   任一失败 → Trial 失败 / 阻断发布

任务门禁：环境 Outcome、必需工具与关键参数
   满足后 → 任务成功

优化指标：表达质量、步骤、延迟、Token、成本
   用于排序和权衡，不抵消硬失败
```

## 数据集必须代表任务分布和失败分布

初始评测集不需要等待数百条完美样本。可以从开发人员已经手工检查的场景、产品需求、Bug、支持工单和早期日志开始，先形成一个可执行的小集。Anthropic 的工程建议给出的启动量级是 20～50 个简单真实任务；这是早期实践建议，不是统计充分性的通用保证。系统成熟、改进幅度变小时，需要更多样本和置信区间才能区分真实变化与噪声。

数据集应同时覆盖：

- 正常主路径和高频用户意图；
- 缺少参数、歧义、用户中途修正和取消；
- 工具超时、空结果、Schema 变化和部分失败；
- 权限边界、Prompt Injection 和高风险副作用；
- 历史回归、长尾组合和成本压力场景。

每个 Task 要有明确、可实现的成功标准。若题目没有要求输出文件路径，Grader 却只在某个固定路径查找，那么测到的是测试缺陷，不是 Agent 能力。测试环境也必须可重置：时间、账户余额、库存、数据库初态和工具响应若在 Trial 间漂移，结果就无法比较。

### 开发集、保留集与线上样本

开发集允许团队查看并快速调试；保留集用于判断泛化和发布，不应在每次调 Prompt 时反复查看答案。线上日志用于发现真实分布和未知故障，但进入数据集前必须脱敏、取得合适授权、去重，并冻结必要的外部资料或时间语义。

同一用户请求的轻微改写不能横跨训练、开发和保留分区，否则会产生数据泄漏。模型、Prompt、RAG 索引或 Fine-tuning 数据也可能见过公开 Benchmark，因此公开分数应与自有业务集分开解释。

标签不是装饰。按意图、工具、风险、语言、长度和故障类型分层后，团队才能发现总分上升其实掩盖了某个关键场景下降。平均数永远不能替代最小切片和高风险切片报告。

## Grader 应优先使用最直接的证据

Agent Eval 通常组合三类 Grader：

| 类型 | 适合任务 | 优点 | 主要风险 |
| --- | --- | --- | --- |
| 代码评分器 | 数据库状态、Schema、单元测试、工具和预算 | 快、便宜、可复现、易调试 | 对合理变体僵硬，难判断开放质量 |
| 模型评分器 | 覆盖度、连贯性、开放答案和成对比较 | 可扩展，能处理语义差异 | 有偏差、随机、受提示和输入污染 |
| 人工评分器 | 专家正确性、主观质量和高风险复核 | 最贴近真实专业判断 | 慢、贵，也可能存在标注分歧 |

原则是先使用距离真相最近、最确定的证据。代码是否可运行就执行测试，数据库是否变化就查数据库，引用是否支持主张就检查引用内容；不要让另一个 LLM 猜测这些确定事实。开放式解释没有唯一字符串答案时，再使用 Rubric-based Model Grader 或人工判断。

Exact Match 适合 ID、枚举和标准化字段，不适合所有自然语言。BLEU、ROUGE 或字符串相似度可以衡量某些表面特征，却不能单独代表事实正确、工具安全或用户目标完成。评分方式必须与成功定义对齐。

### 校准模型评分器

模型评分器不是把“请判断好不好”发给更强模型。一个可维护的 Grader 至少要有明确 Rubric、离散标签或分数锚点、必要证据、无法判断的处理方式和简短理由。相比无约束生成，分类、按标准打分和成对比较通常更容易获得一致判断。

校准流程可以是：专家先标注一批代表性样本；模型评分器在不看专家结论的情况下打分；统计误报、漏报和分歧切片；修改 Rubric 后重新测试；上线后持续抽样复核。单一总体一致率可能掩盖安全类别的严重漏报，因此要按标签查看混淆矩阵。

被评内容可能包含指令注入，Grader 输入也要清晰隔离数据与评分规则。评分模型、Prompt 和 Rubric 都必须版本化；否则被测 Agent 没变，仅评分器漂移也会制造虚假的趋势。

## Trace 评分负责定位，不替代 Outcome

Trace Grading 对模型调用、工具选择、参数、Handoff、Guardrail 和状态转换分配结构化标签。它非常适合回答：错误发生在检索、决策、工具执行还是结果解释？OpenAI 当前 Agent Eval 文档也把 Trace Grading 作为调试工作流行为的重要入口。

但参考轨迹不应成为唯一合法轨迹。Agent 可能找到更短、更安全的新方案；若 Grader 要求完全匹配固定步骤，它反而抑制有效能力。更稳妥的轨迹断言包括：必须查权限、不能调用某工具、参数必须来自已验证 ID、写操作最多一次，以及审批必须早于副作用。

第 09 章会展开 Trace 的数据模型、Span、关联和可观测性。本章只规定 Eval Harness 必须能取得足以评分的执行证据，并把 Grader 失败关联到具体事件。

## 非确定性要求重复 Trial

相同 Task 的模型输出和工具路径可能在多次运行间变化。只跑一次无法区分稳定能力和偶然成功。除了总体 Trial Success Rate，还可以计算两个方向相反的指标：

```text
pass@k：每个 Task 的 k 次 Trial 中至少一次成功，再对 Task 求比例
pass^k：每个 Task 的 k 次 Trial 全部成功，再对 Task 求比例
```

`pass@k` 随尝试机会增加通常上升，适合代码候选生成或允许系统自动挑选多个方案的场景。`pass^k` 随 k 增加通常下降，衡量连续多次都正确的可靠性；该指标由 τ-bench 用于评估工具 Agent 的一致行为。用户每次只获得一次回答时，报告漂亮的 `pass@10` 没有直接产品意义。

重复次数、采样参数、环境初态和并发条件必须记录。不同 k 的数值不能直接比较；用观察到的少量 Trial 简单估计概率时也应给出样本量和不确定性。成本有限时，高风险或高方差 Task 可以获得更多重复，而不是平均分配。

## 能力集和回归集承担不同职责

Capability Eval 应包含当前系统经常失败但有价值的任务，用于推动能力边界；低初始分数不是坏事。Regression Eval 则保护已经承诺给用户的行为，应接近稳定通过，并在每次模型、Prompt、工具或 Runtime 变更时执行。

一次改进的正确流程是：先在能力集上发现并解决问题，再确认其他回归项没有下降，最后把已稳定的新能力及其失败变体加入回归集。只保留越来越容易的测试会形成饱和，只有越来越难的能力集又无法保护旧功能，两套集合需要同时维护。

发布门禁不必要求所有软指标单调上升，但必须预先定义取舍。例如：

```text
发布条件
├── 安全硬门禁：0 个越权或禁止副作用
├── 核心回归集：pass@1 不低于基线容差
├── 关键切片：每个切片达到最低阈值
├── 可靠性：pass^3 达到产品要求
└── 预算：P95 延迟与平均成本没有越界
```

阈值应在看新结果前确定。否则团队容易在回归后临时改变口径。模型升级还要同时冻结并记录旧、新配置，在相同数据和环境上进行配对比较；仅比较两个不同日期的线上均值会混入流量变化。

## 最小 Eval Harness

仓库中的 [`eval_harness.py`](../../examples/08-agent-evals/eval_harness.py) 使用 Python 标准库实现 Task、Trial、Event 和三个确定性 Grader。`OutcomeGrader` 检查环境状态，`ToolPolicyGrader` 检查必需与禁止调用及参数，`BudgetGrader` 检查步骤和成本。

一个 Trial 只有在所有硬 Grader 通过时才成功：

```python
trial = runner(task, attempt)
grades = tuple(grader.grade(task, trial) for grader in graders)
passed = all(grade.passed for grade in grades)
```

多个 Trial 按 Task 聚合：

```python
trial_success_rate = passed_trials / all_trials
pass_at_k = tasks_with_any_success / all_tasks
pass_pow_k = tasks_with_all_success / all_tasks
```

示例还按 Tag 汇总 Trial 成功率，使核心与边界场景不会只剩一个总分。9 个单元测试验证了环境 Outcome 优先于最终自述、工具参数与禁用工具、步骤和成本门禁、多 Trial 指标、组合评分、标签聚合以及无效数据集输入。

它仍是教学实现：没有并发执行、环境快照、置信区间、持久化 Trace、模型 Grader、人工队列或基线比较服务。生产 Eval Harness 还要保证每个 Trial 的环境隔离和清理，限制被测 Agent 读取参考答案，并保存完整版本清单。

## Eval-driven Development 是持续反馈环

评测驱动开发（Eval-driven Development）的重点不是“先把所有测试写完”，而是让每个重要变化都能被测量：

```text
产品要求与线上失败
        ↓
新增或修正 Task、Grader
        ↓
复现失败并形成基线
        ↓
修改 Prompt / Tool / Context / Runtime / Model
        ↓
运行能力集、回归集和风险门禁
        ↓
分析 Trace 与切片 → 发布、回滚或继续迭代
```

OpenAI 的官方评测实践强调尽早、持续、任务特定地评测，并用人工反馈维持自动评分的一致性。这里的“持续”也包括维护评测本身：失真的 Task 要修正但保留版本记录，饱和能力集要增加难例，新出现的线上失败要转成可复现用例。

一次分数提升只说明某个系统版本在某个数据集、环境和 Grader 组合下表现更好。只有版本齐全、差异可定位、风险门禁通过且线上分布得到持续验证时，它才足以支持工程决策。下一章将建立完整 Tracing 与 Observability，使每个 Trial 和生产 Run 都保留可诊断证据。
