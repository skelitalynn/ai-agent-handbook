# AI Agent 全局知识地图

## 1. 这份地图解决什么问题

`SUMMARY.md` 规定教材从前到后的学习顺序，本文件负责展示概念分类、系统组件和跨章节依赖。两者不能混为一份目录：学习顺序强调能力递增，知识地图强调同一概念在完整系统中的位置。

读者在开始学习具体章节前，应先建立一个最小但完整的 Agent 心智模型：Agent 不是一个独立模型名称，而是围绕业务目标组织模型调用、上下文、工具、状态和控制逻辑的运行系统。

## 2. Agent 系统骨架

下面的骨架贯穿全书。后续章节只是在逐步拆解、实现和强化其中的组件。

```text
                         用户与业务目标
                               ↓
┌──────────────────────────────────────────────────────────┐
│                    Agent Application                     │
│                                                          │
│  用户交互 · API · 权限入口 · 结果展示 · 人工审批           │
└──────────────────────────┬───────────────────────────────┘
                           ↓
┌──────────────────────────────────────────────────────────┐
│                      Agent Runtime                       │
│                                                          │
│  ┌────────────┐       ┌────────────────┐                 │
│  │ State /    │ ───→  │ Context Builder│                 │
│  │ Session    │       └───────┬────────┘                 │
│  └─────↑──────┘               ↓                          │
│        │              ┌────────────────┐                 │
│        │              │ Model Gateway  │                 │
│        │              └───────┬────────┘                 │
│        │                      ↓                          │
│        │              文本 / 结构化输出 / Tool Call       │
│        │                      ↓                          │
│  ┌─────┴──────┐       ┌────────────────┐                 │
│  │ Loop /     │ ←──── │ Tool Executor  │                 │
│  │ Workflow   │       └───────┬────────┘                 │
│  └────────────┘               ↓                          │
│                     外部系统、文件与环境                    │
└──────────────────────────────────────────────────────────┘
                           │
              ┌────────────┼─────────────┐
              ↓            ↓             ↓
           Evals         Tracing      Reliability
                                      Security
```

这张图需要建立六个基本判断：

1. 模型负责根据可见输入生成候选文本、结构化结果或行动请求，不直接等于完整 Agent。
2. State 是系统保存的事实和执行状态；Context 是从 State、历史和外部知识中选择后交给模型的有限视图。
3. 模型提出 Tool Call，Runtime 校验并执行；外部副作用不应由模型输出直接触发。
4. Agent Loop 决定观察、行动、写回和终止；Workflow 用确定性结构约束其中部分路径。
5. RAG、Memory、MCP、Skills 和 Multi-Agent 都是在骨架上扩展某一条能力，不是彼此平行的流行名词。
6. Evals、Tracing、Reliability 和 Security 不是最后上线时才补充的章节，而是贯穿每层的工程约束。

## 3. 六个核心问题域

| 问题域 | 核心问题 | 对应组件 |
|---|---|---|
| 模型与生成 | 模型如何表示输入、生成输出并暴露推理服务 | Transformer、Model API、Prompt、Structured Output |
| 行动 | 模型如何提出行动，系统如何安全执行 | Tool Calling、Tool Executor、Sandbox、Computer Use |
| 状态与上下文 | 系统保存什么，本次给模型看什么 | State、Session、Checkpoint、Context Builder |
| 知识与记忆 | 外部事实和历史经验怎样被保存与召回 | Retrieval、RAG、Memory、Files、Artifacts |
| 控制与协作 | 系统如何分解、调度、暂停、恢复和协作 | Agent Loop、Planning、Workflow、Human-in-the-loop、Multi-Agent |
| 质量与治理 | 如何判断有效、定位失败并控制风险 | Evals、Tracing、Reliability、Security、Production Infrastructure |

Runtime、Harness、Framework、MCP、Skills 和 A2A 横跨多个问题域，只有在读者理解基本 Agent Loop、Tool、State 和 Context 后再学习，才不会把产品抽象误当成底层原理。

## 4. 能力递增路径

全书采用“先看完整骨架，再逐层增加能力”的顺序，而不是先罗列完所有概念再组装。

```text
理解完整 Agent 系统
        ↓
理解模型如何生成
        ↓
完成一次受控模型调用
        ↓
实现最小 Agent Loop
        ↓
加入 Tool、State 与 Context
        ↓
建立 Evals 与 Trace
        ↓
加入 RAG 与 Memory
        ↓
处理 Planning、Workflow 与协作
        ↓
理解 Runtime、Harness 与协议扩展
        ↓
设计可靠、安全、可部署的产品
```

每一篇都应产生一个阶段性完整结果，后续篇章在这个结果上增加能力，而不是让读者长期积累无法运行的孤立术语。

## 5. 各篇在骨架中的位置

### 第 00 章：先看到完整系统

第 00 章不是普通阅读说明，而是全书的骨架章节。它应展示最小 Agent 的完整数据流、组件职责、失败边界和后续章节地图。读者暂时不需要掌握每个组件的细节，但需要知道它们为何存在、如何连接。

### 第一篇：模型如何完成一次受控生成

这一篇沿单次模型调用展开：文本如何进入 Transformer，模型如何形成输出，推理服务如何表示消息、事件和用量，以及 Prompt 和输出验证如何把概率生成约束成业务可消费的结果。

阶段成果：实现一个能够记录 Usage、检查停止原因并验证结构化输出的模型客户端。

### 第二篇：模型调用如何形成 Agent 闭环

这一篇从最小 Agent Loop 开始，再分别深入 Tool、State 和 Context。先让读者看到行动—观察—继续或终止的完整循环，再解释每个组件如何可靠实现。

```text
State 保存完整运行事实
   ↓
Context Builder 选择本轮可见内容
   ↓
模型决定回答或提出 Tool Call
   ↓
Runtime 校验并执行工具
   ↓
工具结果写回 State
   ↓
Loop 判断继续、失败或结束
```

阶段成果：实现一个具有工具参数校验、步数限制、明确终止状态和可恢复 Session 的单 Agent。

### 第三篇：先建立测量和调试能力

Evals 定义什么叫成功，Tracing 保留为什么成功或失败的证据。它们位于 RAG、Memory、Planning 和 Multi-Agent 之前，使后续每次增加复杂度都有回归基线和诊断手段。

阶段成果：建立最小任务集、评分规则和完整 Run Trace。

### 第四篇：接入外部知识与长期信息

Retrieval/RAG 解决从外部数据中选择本次相关证据，Memory 解决哪些跨会话信息值得保存、更新和召回。二者都依赖已经建立的 State、Context、Evals 和 Trace。

阶段成果：实现有权限过滤、引用和回归评测的知识型 Agent，并为长期记忆定义写入、更新、召回和删除策略。

### 第五篇：控制复杂任务与协作

Planning 讨论模型怎样决定下一步，Workflow 讨论代码怎样约束执行路径，Human-Agent Interaction 讨论人在何处澄清、审批和接管，Multi-Agent 再讨论何时值得引入多个独立上下文和执行者。

阶段成果：能够根据任务确定性、失败代价和并行需求选择普通代码、Workflow、单 Agent 或 Multi-Agent。

### 第六篇：理解运行时、框架和协议

Runtime/Harness 先解释循环、状态、权限、环境和扩展如何组合；Framework 随后映射这些底层机制；MCP、Skills 和 A2A 再分别扩展外部能力接入、可复用工作流和 Agent 间互操作。

阶段成果：能够透过框架名识别其真实运行时职责，并判断普通 API、MCP、Skill 和 A2A 的适用边界。

### 第七篇：形成产品交互

应用架构模式把前述机制组合成真实产品；多模态、Realtime 和 Computer Use 进一步引入事件流、打断、播放状态、视觉输入和高风险环境操作。

### 第八篇：完成生产闭环

Reliability 处理超时、重试、幂等性、恢复和降级；Security 处理不可信输入、权限、隔离和审计；Production Infrastructure 处理部署、队列、存储、容量、成本和发布。

## 6. 关键概念的归属和前后引用

同一概念可以在多个章节出现，但每次承担不同职责：

| 概念 | 首次建立 | 后续深化 |
|---|---|---|
| Token、Embedding、Transformer | 第 01 章：完整生成计算链 | 第 02 章：上下文、延迟与成本 |
| Chain-of-Thought | 第 01 章：测试时推理机制和边界 | 第 03 章：Prompt 使用；第 08 章：评测 |
| Tool Calling | 第 04 章：最小 Agent Loop 中的行动接口 | 第 05 章：Schema、权限、副作用和执行工程 |
| State | 第 04 章：循环中的最小状态 | 第 06 章：Session、Checkpoint 和一致性 |
| Context | 第 04 章：模型可见输入 | 第 07 章：选择、压缩、隔离和预算 |
| RAG | 第 10 章：外部证据进入 Context | 第 11 章：Memory 的召回基础 |
| Planning | 第 04 章：模型选择下一步 | 第 12 章：分解、重规划、停止和控制边界 |
| Human Approval | 第 05 章：高风险工具执行边界 | 第 14 章：完整的人机交互生命周期 |
| Evals 与 Trace | 第 00 章：贯穿全书的反馈环 | 第 08～09 章：系统方法和实现 |

首次建立只提供理解当前闭环所需的最小概念；后续章节负责完整机制。后文必须链接前文，不能复制一套略有差异的定义。

## 7. 文章拆分原则

文章优先保持一条完整因果链，不按术语层级机械拆分。例如，解释 Transformer 语言模型时，下面的计算过程默认属于同一篇：

```text
文本
→ Tokenization
→ Token ID
→ Embedding + Position
→ Transformer Blocks
→ 词表 Logits
→ 训练时计算 Next-token Loss
→ 推理时选择 Token 并继续生成
```

只有当某个子主题形成独立问题、独立机制、独立实践和足够内容时才拆分。例如，“Tokenizer 工程”若进一步讨论词表训练、多语言压缩率、词表扩展和自托管兼容，可以成为独立文章；仅为了先定义 Token 和 Embedding，不应打断完整生成链。

## 8. 使用方式

- 第一次学习：先读第 00 章和本文，再严格按 `SUMMARY.md` 顺序推进。
- 已有经验但知识零散：先用系统骨架定位薄弱组件，再回到对应章节补齐前置依赖。
- 面试复习：从 `SUMMARY.md` 进入第 01 章及后续正文的面试速记；第 00 章只作为系统 Overview，不改变教材正文顺序。
- 方案设计与排障：从问题域和组件图定位责任层，再查对应章节的工程边界。
