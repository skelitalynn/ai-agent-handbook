# 内容规范

> 本文件是正文模板、标题结构、写作风格、代码、图表、引用和完整性检查的唯一事实来源。修改文章模板时只修改本文件；`PROMPT.md`、`CONTENT_ARCHITECTURE.md`、`PROJECT.md`、`README.md`、`AGENTS.md`、既有正文和对话中的旧约定不得复制或覆盖这里的规则。发生冲突时，以生成任务开始时重新读取到的本文件最新内容为准。

## 1. 文档粒度与标题

一个可以独立建立的心智模型，或一组共同解释同一计算过程、系统边界或工程决策的高度相关问题，对应一篇 Markdown。

篇目录、正文文件和文内小节的划分方法，以及三条阅读路线，遵守 [内容架构设计](CONTENT_ARCHITECTURE.md)。`chapters/` 下的一级子目录对应一篇，目录内正文使用 `NN｜正文标题.md` 命名，编号在全书范围连续；`SUMMARY.md` 直接链接正文文件。`README.md` 不默认创建，也不得承载正式正文。

文件标题优先使用陈述性的知识主题，例如“Transformer 与自回归生成”，不为套用问答格式制造宽泛、异质或显而易见的概念对比。面试题属于文章内的阅读入口，不决定文件边界。

不要：

- 一道面试题一个文件
- 一个简单术语一个文件
- 为减少文件数量，把多条无法连续推导的认知主线塞进同一正文
- 在同一篇中混入多个无关主题
- 为了使用“X 和 Y 有什么区别”的标题而并列不同层级的概念

## 2. 面试速记与教材结构

第 01 章起，每篇正文由面试速记和按主题自由组织的教材层构成。第 00 章是全书 Overview，不设置面试层，标题和导语后直接进入教材正文。

### 2.1 面试层

```markdown
# 陈述性的知识主题

> 本文解决的问题，以及它与本章其他文章的关系。

## 面试速记

### 背诵提纲

**1. 定义**

使用简短、准确、可以直接背诵的完整句子给出定义。

**2. 完整链路**

使用一条简短流程建立计算、执行或数据主线。

**3. 一组相关的关键机制**

- **机制 A**：用一句话说明定义或作用。
- **机制 B**：用一句话说明定义或作用。

### 高频对比

只在概念容易混淆、能够按相同维度比较且具有面试或工程判断价值时保留；否则省略。

### 高频问题

#### 问题1：沿主问题继续深入的问题

用 1～3 句话给出回答要点。

#### 问题2：考察边界、失败或工程取舍的问题

用 1～3 句话给出回答要点。

---
```

- “背诵提纲”以恢复教材知识骨架为目标，不把教材正文缩写一遍，也不能只写一段抽象总结。
- 提纲通常使用 6～10 个从 `1` 开始连续编号的一级知识块；简单主题可以更少，复杂主题应优先把相关概念分组，不把大量术语平铺成同级编号。
- 一级块使用 `**1. 定义**` 这类加粗编号，不使用四级标题。每个一级块通常包含 1～4 个二级概念。
- 二级概念使用加粗名称作为记忆锚点，原则上只用一句话说明最核心的定义、作用或边界。
- 提纲使用短而完整的句子，可以直接背诵，但不能为了简短而省略必要限定；长推导、例子、实现、次要边界和工程细节放入高频对比、高频问题或教材正文。
- 同一信息不在提纲、高频对比和高频问题中反复展开；提纲只保留恢复知识结构所需的最小线索。
- 提纲内部结构随主题变化。算法、协议、系统和安全主题不强制使用同一组“定义、特点、优缺点、场景”字段。
- “高频对比”可以省略。只比较容易混淆且处于可比维度的概念，不把不同系统层级或仅仅相邻的术语强行放进表格。
- “高频问题”列出 3～5 个面试官围绕背诵提纲中的核心机制可能继续提出的问题，每个问题必须提供简短回答要点。
- 问题应沿主问题继续深入，重点考察工作原理、适用边界、方案取舍、异常失败、调试评测和生产落地，不能只是罗列同一领域的其他术语。
- 基础定义、分类和直接枚举由背诵提纲承担；高频问题不重复这些内容，而应继续追究原因、代价、失败条件和验证方法。
- 每个问题及其答案都应由教材正文支撑，不能在面试层临时增加正文没有解释的新主题。
- 面试层用于压缩教材结论，不得先写一套口号再让正文给出不同或相反的限定。
- 第 00 章不得保留空的面试标题、问题或分隔线。

高频问题不能只是横向罗列相邻术语。例如，下面的问题没有沿同一机制深入：

```text
什么是 Tool Calling？
什么是 ReAct？
Agent 有哪些类型？
有哪些 Agent 框架？
什么是 Multi-Agent？
```

以“Agent Loop 如何运行”为主题时，更合适的问题应继续考察终止、循环原因、并行条件、适用边界和故障定位：

```text
如何判断 Agent Loop 应该终止？
为什么设置最大步数仍然不能彻底解决死循环？
多个工具调用什么时候可以并行？
什么情况下不应该使用 Agent Loop？
如何判断一次 Agent 失败是模型问题还是工具问题？
```

每个问题仍须按照前述模板提供 1～3 句话的回答要点，完整答案由教材正文支撑。

### 2.2 教材层

分隔线后进入完整正文。教材层不强制使用统一的二级标题，应根据主题选择自然结构：

- 算法和原理：问题、推导、最小实现、复杂度、工程影响。
- API 和协议：角色或对象、消息、生命周期、状态、错误、版本和安全。
- 系统架构：约束、组件、数据流、失败模式、权衡和验证。
- 安全：资产、信任边界、威胁、控制措施和剩余风险。

教材层可以按照文章自身结构使用少量二级、三级标题和分点，但必须服务于阅读和推导：

- 段落是默认表达方式，连续论述不要拆成碎片化列表。
- 多个内容确实并列、需要比较或构成步骤时才使用分点。
- 不为形式统一机械添加“定义、原理、实践、误区”等标题。
- 不使用只有一句话的小节、只有一个条目的列表或连续多层嵌套列表。
- 一个小节应承担一个清晰的论证、过程或决策问题，而不是只容纳一个术语。

教材层通常需要覆盖以下问题，但不要求机械按此顺序设标题：

- 主题为什么产生，它在完整知识图谱中的位置是什么。
- 核心对象、状态、执行过程或推导是什么。
- 结论如何从机制推导出来。
- 如何通过最小实现、实验或案例验证关键机制。
- 对正确性、延迟、成本、安全和可维护性有什么影响。
- 与相邻概念的边界是什么，常见误区为什么错误。
- 学完后读者应当能够解释、实现或判断什么。

在有助于解释工作原理、执行顺序、组件关系或方案差异时，可以补充纯文本流程图、纯文本时序图、纯文本架构图和 Markdown 表格。

流程图、时序图和架构图必须放在 `text` 代码块中，通过箭头、缩进、分支和简单框线表达。例如：

```text
用户请求
   ↓
调用模型
   ↓
是否需要调用工具？
   ├── 否 → 返回最终答案
   └── 是
         ↓
      执行工具
         ↓
      写回工具结果
         ↓
      再次调用模型
```

使用规则：

- 流程图表示步骤、条件和循环。
- 时序图表示参与方之间按时间发生的消息和状态变化。
- 架构图表示组件、边界、依赖和数据流向。
- Markdown 表格比较多个对象在相同维度上的差异。
- 图表必须补充正文难以快速表达的关系，不能只是重复相邻段落。
- 图表前后应说明观察重点；关系简单时优先使用正文，不为装饰强行添加图表。

**公式和符号必须跨平台可读**

- 正文不使用 `$...$`、`$$...$$`、`\(...\)`、`\[...\]` 或其他依赖 LaTeX、MathJax、KaTeX 的公式语法；仓库 Markdown、代码预览和发布端不能假设具有相同的数学渲染能力。
- 简短变量和表达式使用行内代码，例如 `T`、`d`、`P(x[t] | x[1:t])`；需要独立展示的公式放入 `text` 代码块。
- 公式优先使用 Unicode 数学符号和容易辨认的纯文本写法，例如 `∈`、`×`、`Σ`、`√`、`^T` 和 `_`。如果紧凑符号会提高理解门槛，应改写为展开式、步骤或文字关系。
- 公式前后必须解释变量含义、计算顺序和它支持的结论，不能要求读者仅靠符号自行恢复推导。

### 2.3 教学叙事、标题层级与术语引入

教材层的“完整”是建立一条能从问题推导到结论的主线，不是把所有相关概念放进同一篇文章。面向尚未建立完整 Agent 知识框架的读者时，默认按以下方式组织教学。

**先建立全貌，再进入局部**

- 正文开头先说明要解决的具体问题、前置能力和完整过程，让读者知道当前章节在全书中的位置。
- 主题存在清晰执行链、数据流或因果链时，先给出一张紧凑的全局流程图，后续小节再按该顺序展开。
- 每个主要小节都应能回答“我们现在走到了完整链路的哪一步”，不让读者自行拼接概念之间的关系。

**先出现问题，再引入概念**

- 默认叙事顺序是“具体场景或失败 → 为什么会失败 → 解决机制 → 术语名称 → 适用边界”。
- 不用一个未解释的抽象名词定义另一个抽象名词，也不在连续段落中一次投放大量新术语。
- 适合时选择一个足够小的贯穿案例，让后续机制逐步解决该案例中暴露的问题；不为每个术语换一个与主线无关的新案例。
- 某项内容已由后续章节专门讲解时，当前章只保留理解主线必需的结论、边界和章节引用，不抢先展开另一套知识体系。

**用标题层级表达知识关系**

- 二级标题表示完整主线中的主要阶段或大问题，三级标题表示该阶段下必须解决的子问题。
- 具有父子、先后或依赖关系的内容不能全部平铺为同级标题。长文章在编号能帮助读者定位主线时，可使用 `1`、`1.1` 这类连续编号，但不强制所有文章统一编号。
- 标题应尽量表达正在解决的问题或执行的动作，例如“先定义什么结果算成功”，而不是只列出“成功标准”这类孤立名词。
- 完成初稿后单独阅读所有教材层标题；如果只看标题仍无法复原主线，说明层级或顺序仍需调整。

**专业但不用术语制造阅读门槛**

- 优先使用短而完整的句子表达一个主要关系，一段只推进一个子问题；不用长句同时压入多个机制、限定和例外。
- 必要英文术语首次出现时，先用直白中文说明它解决什么问题，再给出英文名称。后续使用稳定称呼，不反复堆叠中英文同义表达。
- 行业中主要使用英文、中文直译生硬或容易误解时，直接保留英文。例如第 03 章使用 `Prompt Contract`、`Input Contract` 和 `Output Contract`，不使用“提示词契约”、“输入契约”或“输出契约”。
- 不为了形式对称发明或强行使用术语。例如不使用少见的 `Failure Contract`，而是根据语境写“失败处理”、`Failure Handling` 或 `Recovery Policy`。
- 官方定义、行业常用术语和本书自定义抽象必须区分。本书自定义的组织方式在首次出现时明确说明，不写成厂商或学界的正式定义。

**分点和图表用来降低认知负担**

- 连续推导使用段落，执行顺序使用编号或流程图，多个对象按相同维度比较时使用表格，确实并列的短内容才使用项目符号。
- 表格和分点应让读者更快看出差异、顺序或分类，不把本可以连续说清的文章拆成一页孤立句子。
- 不追求固定数量的标题、分点或图表。它们的数量由主题本身的阶段、分支和比较关系决定。

## 3. 写作风格

- 专业、清晰、克制
- 先给结论，再讲原理
- 面向有 CS 或后端基础、希望系统转向 AI Agent 并准备求职的读者
- 不写编程语言入门、通用环境安装或与主题无关的逐行教学，但必要的模型与 Agent 前置原理必须完整建立
- 不写行业套话和宏大背景
- 不刻意幽默，不使用网络梗
- 不堆砌英文术语
- 英文术语首次出现时给出中文解释
- 区分官方定义、行业常见做法和工程建议
- 先解释厂商无关的核心机制，再说明具体厂商或框架的实质差异
- 用连续叙事建立知识依赖，不把正文写成互不关联的正确句子集合
- 使用少量、必要的标题和分点帮助阅读，不为了结构化而结构化
- 允许同一概念在不同章节承担不同用途，但后文引用前文，不大段重复
- 不在结尾机械添加总结

## 4. 代码要求

- 原理说明优先使用最小实现代码，不默认使用抽象伪代码
- 最小实现应尽量可运行或接近可运行；必须抽象时才使用伪代码
- 可运行示例默认使用 Python
- 只有浏览器、Node.js 或 TypeScript SDK 特有主题使用 TypeScript
- 涉及语言差异时再提供对照说明，不强制维护双语言示例
- 不使用高层框架隐藏当前主题
- 教学代码不得冒充生产代码
- 第三方 SDK 示例标注核验日期
- 可运行示例放入 `examples/`，正文只保留关键部分

## 5. 引用要求

优先级：

1. 协议规范和官方文档
2. 原始论文
3. 官方工程博客
4. 官方代码仓库
5. 高质量课程和技术文章

版本或来源发生冲突时，以最新正式稳定版本和最新官方资料为主。预览版、Beta 和实验特性单独标注；已废弃但仍有辨识价值的旧概念仅简短保留，并写明适用版本、废弃状态和最后核验日期。

参考资料必须是正文实际使用的来源。来源权威不代表与正文自动相关；没有在正文中解释或核对其核心结论的论文、规范和文档不得作为装饰性引用列出。

参考资料必须写明：

- 标题
- 来源
- 链接
- 用于核对的内容
- 最后核验日期

对于原理性论文，应说明正文具体使用了论文中的哪个机制或结论。对于快速变化的 API，应同时检查 API Reference、功能指南、模型限定条件和近期 Release Notes；不能只依据一个页面写出无条件的跨模型结论。

## 6. 完整性检查

一篇文章不是因为包含固定数量的小节而完整。提交初稿前检查：

- 第 01 章起，背诵提纲是否使用连续编号和合理分组，能以最小线索恢复正文主干并包含必要限定。
- 二级概念是否原则上压缩为一句话，详细解释是否已经留给对比、问题或教材正文。
- 高频对比是否确有可比维度和判断价值；没有时是否已经省略。
- 3～5 个问题是否沿主问题形成深入链路，并分别提供了回答要点。
- 正文是否建立了一个完整的心智模型，而不是只列术语和结论。
- 关键前置知识是已经讲解、明确引用，还是仍然缺失。
- 最小实现、实验或案例是否真正验证了文章的核心机制。
- 文章是否解释了工程后果和失败边界。
- 标题、分点和图表是否确实改善理解，而不是把正文碎片化或重复表达。
- 公式是否使用不依赖 LaTeX 渲染器的行内代码或 `text` 代码块，并解释了变量、计算顺序和结论。
- 只阅读教材层标题时，是否能复原文章的完整主线，父子、先后和依赖关系是否已由标题层级表达。
- 新术语是否在具体问题和机制之后引入，是否存在用抽象名词解释抽象名词或连续堆叠未解释英文的段落。
- 贯穿案例是否真正帮助后续机制逐步解决问题，而不是只在开头出现一次。
- 已有后续专门章节的内容，是否只保留了当前主线必需的结论、边界和引用。
- 参考资料是否与正文中的具体结论对应。
- 正文路径、连续编号和标题是否与 `SUMMARY.md` 一致。
- 正文是否自行说明了它在全局骨架中的位置、前置能力和学完后的阶段成果。
