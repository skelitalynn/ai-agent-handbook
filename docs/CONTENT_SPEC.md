# 内容规范

## 1. 文档粒度与标题

一个可以独立建立的心智模型，或一组共同解释同一计算过程、系统边界或工程决策的高度相关问题，对应一篇 Markdown。

篇目录、正文文件和文内小节的划分方法，以及三条阅读路线，遵守 [内容架构设计](CONTENT_ARCHITECTURE.md)。`chapters/` 下的一级子目录对应一篇，目录内正文使用 `NN｜正文标题.md` 命名，编号在全书范围连续；`SUMMARY.md` 直接链接正文文件。`README.md` 不默认创建，也不得承载正式正文。

文件标题优先使用陈述性的知识主题，例如“Transformer 与自回归生成”，不为套用问答格式制造宽泛、异质或显而易见的概念对比。面试题属于文章内的阅读入口，不决定文件边界。

不要：

- 一道面试题一个文件
- 一个简单术语一个文件
- 为减少文件数量，把多条无法连续推导的认知主线塞进同一正文
- 在同一篇中混入多个无关主题
- 为了使用“X 和 Y 有什么区别”的标题而并列不同层级的概念

## 2. 面试速记与教材结构

第 01 章起，每篇正文由面试速记和按主题自由组织的教材层构成。第 00 章是全书 Overview，不设置面试层，标题和导语后直接进入教材正文。

### 2.1 面试层

```markdown
# 陈述性的知识主题

> 本文解决的问题，以及它与本章其他文章的关系。

## 面试速记

### 背诵提纲

**定义**

使用简短、准确、可以直接背诵的完整句子给出定义。

**完整链路或关键机制**

根据主题继续列出流程、组件、分类、边界和工程影响。使用加粗概念作为记忆锚点，不机械套用固定字段。

### 高频对比

只在概念容易混淆、能够按相同维度比较且具有面试或工程判断价值时保留；否则省略。

### 高频问题

#### 问题1：沿主问题继续深入的问题

用 1～3 句话给出回答要点。

#### 问题2：考察边界、失败或工程取舍的问题

用 1～3 句话给出回答要点。

---
```

- “背诵提纲”必须覆盖教材主干，通常包括定义、完整链路、关键机制、必要分类、边界和工程影响，不能只写一段抽象总结。
- 提纲使用短而完整的句子，可以直接背诵，但不能为了简短而省略必要限定；不放长推导、实现代码、论文历史或装饰性引用。
- 提纲内部结构随主题变化。算法、协议、系统和安全主题不强制使用同一组“定义、特点、优缺点、场景”字段。
- “高频对比”可以省略。只比较容易混淆且处于可比维度的概念，不把不同系统层级或仅仅相邻的术语强行放进表格。
- “高频问题”列出 3～5 个面试官围绕背诵提纲中的核心机制可能继续提出的问题，每个问题必须提供简短回答要点。
- 问题应沿主问题继续深入，重点考察工作原理、适用边界、方案取舍、异常失败、调试评测和生产落地，不能只是罗列同一领域的其他术语。
- 基础定义、分类和直接枚举由背诵提纲承担；高频问题不重复这些内容，而应继续追究原因、代价、失败条件和验证方法。
- 每个问题及其答案都应由教材正文支撑，不能在面试层临时增加正文没有解释的新主题。
- 面试层用于压缩教材结论，不得先写一套口号再让正文给出不同或相反的限定。
- 第 00 章不得保留空的面试标题、问题或分隔线。

完整的正反例见 [内容架构设计中的追问设计示例](CONTENT_ARCHITECTURE.md#追问设计示例)。

### 2.2 教材层

分隔线后进入完整正文。教材层不强制使用统一的二级标题，应根据主题选择自然结构：

- 算法和原理：问题、推导、最小实现、复杂度、工程影响。
- API 和协议：角色或对象、消息、生命周期、状态、错误、版本和安全。
- 系统架构：约束、组件、数据流、失败模式、权衡和验证。
- 安全：资产、信任边界、威胁、控制措施和剩余风险。

教材层可以按照文章自身结构使用少量二级、三级标题和分点，但必须服务于阅读和推导：

- 段落是默认表达方式，连续论述不要拆成碎片化列表。
- 多个内容确实并列、需要比较或构成步骤时才使用分点。
- 不为形式统一机械添加“定义、原理、实践、误区”等标题。
- 不使用只有一句话的小节、只有一个条目的列表或连续多层嵌套列表。
- 一个小节应承担一个清晰的论证、过程或决策问题，而不是只容纳一个术语。

教材层通常需要覆盖以下问题，但不要求机械按此顺序设标题：

- 主题为什么产生，它在完整知识图谱中的位置是什么。
- 核心对象、状态、执行过程或推导是什么。
- 结论如何从机制推导出来。
- 如何通过最小实现、实验或案例验证关键机制。
- 对正确性、延迟、成本、安全和可维护性有什么影响。
- 与相邻概念的边界是什么，常见误区为什么错误。
- 学完后读者应当能够解释、实现或判断什么。

在有助于解释工作原理、执行顺序、组件关系或方案差异时，可以补充纯文本流程图、纯文本时序图、纯文本架构图和 Markdown 表格。

流程图、时序图和架构图必须放在 `text` 代码块中，通过箭头、缩进、分支和简单框线表达。例如：

```text
用户请求
   ↓
调用模型
   ↓
是否需要调用工具？
   ├── 否 → 返回最终答案
   └── 是
         ↓
      执行工具
         ↓
      写回工具结果
         ↓
      再次调用模型
```

使用规则：

- 流程图表示步骤、条件和循环。
- 时序图表示参与方之间按时间发生的消息和状态变化。
- 架构图表示组件、边界、依赖和数据流向。
- Markdown 表格比较多个对象在相同维度上的差异。
- 图表必须补充正文难以快速表达的关系，不能只是重复相邻段落。
- 图表前后应说明观察重点；关系简单时优先使用正文，不为装饰强行添加图表。

## 3. 写作风格

- 专业、清晰、克制
- 先给结论，再讲原理
- 面向有 CS 或后端基础、希望系统转向 AI Agent 并准备求职的读者
- 不写编程语言入门、通用环境安装或与主题无关的逐行教学，但必要的模型与 Agent 前置原理必须完整建立
- 不写行业套话和宏大背景
- 不刻意幽默，不使用网络梗
- 不堆砌英文术语
- 英文术语首次出现时给出中文解释
- 区分官方定义、行业常见做法和工程建议
- 先解释厂商无关的核心机制，再说明具体厂商或框架的实质差异
- 用连续叙事建立知识依赖，不把正文写成互不关联的正确句子集合
- 使用少量、必要的标题和分点帮助阅读，不为了结构化而结构化
- 允许同一概念在不同章节承担不同用途，但后文引用前文，不大段重复
- 不在结尾机械添加总结

## 4. 代码要求

- 原理说明优先使用最小实现代码，不默认使用抽象伪代码
- 最小实现应尽量可运行或接近可运行；必须抽象时才使用伪代码
- 可运行示例默认使用 Python
- 只有浏览器、Node.js 或 TypeScript SDK 特有主题使用 TypeScript
- 涉及语言差异时再提供对照说明，不强制维护双语言示例
- 不使用高层框架隐藏当前主题
- 教学代码不得冒充生产代码
- 第三方 SDK 示例标注核验日期
- 可运行示例放入 `examples/`，正文只保留关键部分

## 5. 引用要求

优先级：

1. 协议规范和官方文档
2. 原始论文
3. 官方工程博客
4. 官方代码仓库
5. 高质量课程和技术文章

版本或来源发生冲突时，以最新正式稳定版本和最新官方资料为主。预览版、Beta 和实验特性单独标注；已废弃但仍有辨识价值的旧概念仅简短保留，并写明适用版本、废弃状态和最后核验日期。

参考资料必须是正文实际使用的来源。来源权威不代表与正文自动相关；没有在正文中解释或核对其核心结论的论文、规范和文档不得作为装饰性引用列出。

参考资料必须写明：

- 标题
- 来源
- 链接
- 用于核对的内容
- 最后核验日期

对于原理性论文，应说明正文具体使用了论文中的哪个机制或结论。对于快速变化的 API，应同时检查 API Reference、功能指南、模型限定条件和近期 Release Notes；不能只依据一个页面写出无条件的跨模型结论。

## 6. 完整性检查

一篇文章不是因为包含固定数量的小节而完整。提交初稿前检查：

- 第 01 章起，背诵提纲是否覆盖正文主干、可以直接背诵，并包含必要限定。
- 高频对比是否确有可比维度和判断价值；没有时是否已经省略。
- 3～5 个问题是否沿主问题形成深入链路，并分别提供了回答要点。
- 正文是否建立了一个完整的心智模型，而不是只列术语和结论。
- 关键前置知识是已经讲解、明确引用，还是仍然缺失。
- 最小实现、实验或案例是否真正验证了文章的核心机制。
- 文章是否解释了工程后果和失败边界。
- 标题、分点和图表是否确实改善理解，而不是把正文碎片化或重复表达。
- 参考资料是否与正文中的具体结论对应。
- 正文路径、连续编号和标题是否与 `SUMMARY.md` 一致。
- 正文是否自行说明了它在全局骨架中的位置、前置能力和学完后的阶段成果。
